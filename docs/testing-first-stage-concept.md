# Концепция тестирования решения на первое время

## Цель

На первом этапе тестирование должно снижать риск выхода релизов с ошибками за счет автоматической проверки стабильности кода и раннего выявления регрессий.

Этот подход не предназначен для проверки качества ответов ассистента, релевантности поиска или корректности смысловой интерпретации пользовательских запросов. Для сквозного смыслового тестирования в проекте уже используется отдельное специализированное решение.

## Область применения

В данный подход входят:

- unit-тесты для логики приложения;
- узкие интеграционные тесты на границах модулей, если без них нельзя надежно проверить код;
- регрессионные тесты на исправленные дефекты.

В данный подход не входят:

- смысловое тестирование ассистента;
- оценка качества LLM-ответов;
- проверка релевантности поиска;
- end-to-end сценарии как способ проверки качества ассистента.

## Основные требования

- Тесты должны запускаться локально одной командой.
- На первом этапе допускается ручной запуск перед релизом и перед сборкой.
- Далее этот же набор тестов должен быть включен в автоматический запуск в пайплайне сборки.
- Тесты должны быть быстрыми, стабильными и не зависеть от внешней среды.
- Внешние зависимости должны подменяться моками, стабами или фейками.
- Каждый найденный дефект после исправления должен закрепляться отдельным тестом.

## Какие компоненты покрывать в первую очередь

### 1. Общие модули с чистой логикой

В первую очередь покрываются функции, которые:

- разбирают пользовательский ввод;
- форматируют результаты;
- преобразуют данные между внутренними форматами;
- извлекают служебные метаданные.

Для текущего решения это прежде всего:

- `utils/doc_search_format.py`;
- `bot/services/utils.py`;
- вспомогательные функции в `agent/helpers.py`.

Это самый дешевый и быстрый слой unit-тестов с высокой отдачей.

### 2. Логика маршрутизации и валидации в `agent`

Нужно тестировать:

- валидаторы результатов агентов;
- выбор ветки обработки запроса;
- правила follow-up сценариев;
- работу с `session.state`;
- реакции на пустые и некорректные данные.

Ключевые модули:

- `agent/rootagent.py`;
- `agent/agents/dispatcher_agent.py`;
- `agent/agents/kb_answer_agent.py`;
- `agent/agents/owasp_agent.py`.

Здесь тесты должны подтверждать корректность кодовой логики, а не содержания LLM-ответа.

### 3. Сервисный слой `bot`

Нужно покрывать:

- обработку команд и служебных сценариев;
- пагинацию;
- сценарий скачивания документов по rank;
- сохранение и чтение состояния поиска;
- поведение при ошибках зависимостей.

Ключевые модули:

- `bot/services/handlers.py`;
- `bot/services/database.py`;
- `bot/services/broadcast.py`.

### 4. MCP- и KB-сервисы

Нужно покрывать прикладную логику, которая не должна ломаться при релизе:

- валидацию входных параметров;
- файловые операции;
- правила выбора коллекций;
- обработку метаданных;
- поведение при ошибках Qdrant, storage и HTTP-клиентов.

Ключевые модули:

- `mcps/kb-manager/app/services/file_storage_service.py`;
- `mcps/kb-manager/app/services/qdrant_service.py`;
- `mcps/mcp-server-faq/utils/indexer.py`;
- `mcps/mcp-server-faq/utils/storager.py`;
- `mcps/mcp-server-faq/utils/preprocessors/*`.
- `mcps/mcp-server-kbsearch/app/mcp-server-kbsearch_v2.py`;
- `mcps/mcp-server-kbsearch/app/utils/indexer.py`;
- `mcps/mcp-server-kbsearch/app/utils/storager.py`;
- `mcps/mcp-server-kbsearch/app/utils/preprocessors/*`.

### 5. Авторизация и права доступа в `kb-manager`

Отдельно нужно покрыть:

- проверку токенов;
- правила доступа по ролям;
- middleware авторизации;
- реакции на невалидные и просроченные токены.

## Технический стек

Базовый фреймворк для тестов: `pytest`.

Рекомендуемый стек на первом этапе:

- `pytest`;
- `pytest-asyncio`;
- `unittest.mock` или `pytest-mock`;
- `respx` для мокирования `httpx`, если потребуется.

Выбор `pytest` подходит проекту по следующим причинам:

- он уже используется в репозитории;
- хорошо работает с `async`-кодом;
- позволяет быстро писать и поддерживать тесты;
- хорошо подходит для генерации и сопровождения тестов с помощью assistant.

## Принципы написания тестов

- Один тест проверяет одно правило поведения.
- Тесты должны быть короткими и понятными.
- Подготовка тестовых данных должна быть простой и переиспользуемой.
- Общие фикстуры нужно выносить в `tests/conftest.py`.
- Приоритет у тестов на собственную логику проекта, а не на поведение сторонних библиотек.
- Не нужно пытаться unit-тестами покрыть реальную работу внешних сервисов по сети.

## Порядок внедрения

### Шаг 1

Создать базовую структуру `tests/` и настроить локальный запуск `pytest`.

Состав шага 1:

- создать каталог `tests/` и базовые подпапки по слоям решения;
- уточнить конфигурацию `pytest`;
- вынести тестовые зависимости в отдельный файл;
- добавить общий `tests/conftest.py`;
- зафиксировать единый локальный способ запуска;
- проверить, что тестовый контур стартует без внешних сервисов;
- добавить технический smoke-тест;
- кратко описать правила использования тестового контура;
- зафиксировать критерий завершения шага 1.

### Шаг 2

Покрыть unit-тестами модули с чистой логикой:

- `utils/doc_search_format.py`;
- `bot/services/utils.py`;
- `agent/helpers.py`.

### Шаг 3

Покрыть критичную маршрутизацию и валидацию:

- `agent/rootagent.py`;
- `agent/agents/dispatcher_agent.py`;
- `agent/agents/owasp_agent.py`;
- `agent/agents/kb_answer_agent.py`.

Смысл шага 3:

- проверить первый защитный фильтр цепочки в `owasp_agent`;
- проверить корректность маршрутизации и follow-up логики в `dispatcher_agent`;
- проверить валидацию ответа и контракт результата в `kb_answer_agent`;
- проверить orchestration и работу с `session.state` в `rootagent`.

### Шаг 4

Добавить тесты на сервисный слой `bot` и на критичные части `kb-manager`, `mcp-server-faq` и `mcp-server-kbsearch`.

Смысл шага 4:

- покрыть сервисный слой `bot`, где есть работа с состоянием, пагинацией, скачиванием документов и обработкой ошибок;
- покрыть прикладную логику `kb-manager`, связанную с файловым хранилищем, коллекциями и Qdrant;
- покрыть сервер `mcp-server-faq`, который отвечает за FAQ-поиск, индексацию и обработку связанных данных;
- покрыть сервер `mcp-server-kbsearch`, который отвечает за поиск по базе знаний, контракт результата поиска и обработку ошибок backend-слоя.

### Шаг 5

Подключить запуск тестов в сборку и сделать их обязательной проверкой перед релизом.

## Критерий готовности первого этапа

Первый этап можно считать внедренным, если:

- тесты запускаются одной командой локально;
- покрыты unit-тестами основные модули с бизнес-логикой и маршрутизацией;
- исправленные баги закрепляются регрессионными тестами;
- тесты добавлены в обязательный предрелизный прогон;
- тесты не проверяют смысловое качество ответов ассистента и не дублируют существующее специализированное сквозное тестирование.
