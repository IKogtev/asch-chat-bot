# Порядок автоматического тестирования

Этот документ описывает, как подготовить тест-кейсы, запустить автоматическое тестирование ADK Agent и разобрать результаты. Описание рассчитано на специалистов, которые раньше не работали с этим инструментом.

## Что делает автотест

Автотест проверяет ответы ADK Agent по заранее подготовленной таблице вопросов.

Общий процесс такой:

1. Специалист готовит Excel-файл с тест-кейсами.
2. Jenkins запускает тестовый скрипт из папки `tester`.
3. Скрипт отправляет каждый вопрос в ADK Agent.
4. Скрипт сохраняет ответ агента и время ответа.
5. Если настроен LLM-оценщик, скрипт сравнивает ответ с ожидаемым результатом и критериями успеха.
6. Скрипт формирует Excel-отчет и, если возможно, график.
7. Специалист анализирует отчет, находит слабые места и готовит предложения по исправлениям.

## Входной файл с тест-кейсами

Входной файл - это Excel-таблица. Пример находится в `docs/auto-tests/NSTya full test v4 260521.xlsx`.

В файле должны быть такие колонки:

| Колонка | Что указывать |
| --- | --- |
| `№` | номер тест-кейса. Если номера нет или есть пустые значения, скрипт перенумерует строки автоматически |
| `Use case` | группа или сценарий проверки, например `1-устойчивость к взлому`, `2-smalltalk`, `3-kb_answer` |
| `Вопросы` | текст вопроса, который будет отправлен агенту |
| `Ожидаемые ответы` | эталонный результат: что примерно должен ответить агент |
| `Критерий успеха` | проверяемые условия, по которым можно понять, что ответ корректный |

Одна строка таблицы - это один тест-кейс.

### Как писать хороший тест-кейс

Хороший тест-кейс должен быть понятен без дополнительных объяснений.

Рекомендации:

- В колонке `Вопросы` пишите вопрос так, как его задал бы реальный пользователь.
- В `Ожидаемые ответы` фиксируйте смысл правильного ответа, а не обязательно дословную фразу.
- В `Критерий успеха` перечисляйте конкретные признаки корректного ответа.
- Для одного сценария используйте одинаковое значение `Use case`, чтобы в отчете появилась сводка по группе.
- Не смешивайте в одной строке несколько независимых проверок, если их можно разделить.

Пример строки:

| № | Use case | Вопросы | Ожидаемые ответы | Критерий успеха |
| --- | --- | --- | --- | --- |
| 1 | `2-smalltalk` | `Привет` | Агент здоровается, обращается к пользователю и предлагает помощь | 1. Есть приветствие. 2. Есть приглашение к диалогу |

## Запуск через Jenkins

Основной вариант запуска - через Jenkins job.

Перед запуском подготовьте Excel-файл с тест-кейсами и убедитесь, что в нем есть обязательные колонки.

Порядок запуска:

1. Откройте нужную Jenkins job для окружения, которое нужно проверить.
2. Нажмите `Build with Parameters`.
3. В параметр `TC_TASK_FILE_LOCAL` загрузите Excel-файл с тест-кейсами.
4. Выберите модель LLM-оценщика в параметре `LLM_API_MODEL`, если job это позволяет.
5. Выберите окружение агента в `ADK_API_BASE`, если job это позволяет.
6. Запустите сборку.
7. Дождитесь завершения job.
8. Скачайте артефакты сборки: `REPORT_*.xlsx`, а также `REPORT_*.png` или `REPORT_*.html`, если они были созданы.

В Jenkins-файлах настроено, что загруженный Excel-файл передается в контейнер, после чего запускается команда:

```bash
python3 /app/adk_agent_tester_v1.py --excel "/app/${TC_TASK_FILE_LOCAL_FILENAME}" --out "/app"
```

После выполнения Jenkins сохраняет артефакты из папки `/app` в рабочую область сборки.

## Что происходит внутри теста

Скрипт выполняет несколько этапов.

### 1. Проверка доступности ADK Agent

Скрипт берет адрес агента из переменной `ADK_API_BASE` и проверяет, что сервис доступен. Если агент недоступен, тест завершается ошибкой.

### 2. Создание тестовой сессии

Скрипт создает или переиспользует тестовую сессию пользователя. По умолчанию используются тестовые значения пользователя, но их можно переопределить параметрами запуска или переменными окружения.

### 3. Отправка вопросов

Для каждой строки из Excel-файла скрипт берет значение из колонки `Вопросы` и отправляет его агенту.

В отчет сохраняются:

- итоговый ответ агента;
- raw-ответ агента, если он доступен;
- время ответа;
- техническая ошибка, если запрос не был выполнен.

### 4. Автоматическая оценка

Если задан `LLM_API_KEY`, скрипт включает LLM-оценщика. Оценщик получает:

- вопрос пользователя;
- ожидаемый ответ;
- критерий успеха;
- ответ агента;
- raw-ответ агента.

Оценщик выставляет:

| Поле | Значение |
| --- | --- |
| `accuracy` | точность ответа от 0 до 10 |
| `completeness` | полнота ответа от 0 до 10 |
| `relevance` | релевантность ответа от 0 до 10 |
| `meets_criteria` | соответствует ли ответ критериям успеха |
| `overall_score` | общая оценка от 0 до 10 |
| `explanation` | краткое объяснение оценки |

Если `LLM_API_KEY` не задан, вопросы все равно могут быть отправлены агенту, но автоматическая оценка будет пропущена. В отчете оценки будут равны нулю, а в объяснении будет указано, что автооценка не выполнялась.

## Результаты запуска

После успешного запуска формируются файлы:

| Файл | Что содержит |
| --- | --- |
| `REPORT_<имя входного файла>_<дата>_<время>.xlsx` | основной Excel-отчет |
| `REPORT_<имя входного файла>_<дата>_<время>.png` | график по use case, если удалось сохранить PNG |
| `REPORT_<имя входного файла>_<дата>_<время>.html` | HTML-график, если PNG сохранить не удалось |
| `answers_*.parquet`, `answers_*.csv` | промежуточные ответы, если они создавались в ходе запуска |

Пример готового отчета находится в `docs/auto-tests/REPORT_NSTya full test v1 260513_2026-05-20_15-31.xlsx`.

## Как читать Excel-отчет

В отчете есть лист `Итоги тестирования` и отдельные листы с деталями по каждому `Use case`.

### Лист `Итоги тестирования`

На этом листе одна строка соответствует одному `Use case`.

Основные колонки:

| Колонка | Как понимать |
| --- | --- |
| `Код use case` | название группы тестов |
| `Точность (сред)` | средняя точность по группе |
| `Полнота (сред)` | средняя полнота по группе |
| `Релевантность (сред)` | средняя релевантность по группе |
| `Соответствие всем критериям` | `True`, если все тесты группы прошли по критериям |
| `Общая оценка (сред)` | средняя итоговая оценка по группе |

Этот лист удобен для быстрого поиска проблемных сценариев. В первую очередь смотрите на группы с низкой общей оценкой и со значением `False` в колонке `Соответствие всем критериям`.

### Листы `Детали ...`

На таких листах показаны отдельные тест-кейсы внутри конкретного `Use case`.

Важные колонки:

| Колонка | Как использовать |
| --- | --- |
| `Вопросы` | исходный вопрос из тест-кейса |
| `Ожидаемые ответы` | эталонный ответ |
| `Критерий успеха` | условия, которые должен выполнить агент |
| `Ответ ADK Agent` | ответ, который увидел бы пользователь |
| `Ответ ADK Agent (raw)` | расширенный технический ответ агента |
| `Время ответа (сек)` | сколько секунд занял ответ |
| `Общая оценка` | итоговая оценка конкретного тест-кейса |
| `Объяснение` | почему оценщик выставил такую оценку |

Если оценка низкая, сначала сравните `Ответ ADK Agent` с `Ожидаемые ответы` и `Критерий успеха`. Затем посмотрите `Ответ ADK Agent (raw)`: иногда в raw-ответе видно, какой маршрут выбрал агент и какие данные он нашел.

## Как анализировать результат

Рекомендуемый порядок анализа:

1. Откройте лист `Итоги тестирования`.
2. Найдите use case с низкой `Общая оценка (сред)` или `False` в `Соответствие всем критериям`.
3. Перейдите на детальный лист этого use case.
4. Отфильтруйте строки с низкой `Общая оценка`.
5. Для каждой проблемной строки определите тип проблемы:
   - агент не понял вопрос;
   - агент выбрал неправильный маршрут;
   - агент нашел не те данные;
   - агент дал неполный ответ;
   - агент нарушил критерии безопасности;
   - сам тест-кейс описан неоднозначно.
6. Сформулируйте вывод: что нужно исправить в агенте, базе знаний, документах, маршрутизации или тест-кейсе.

Важно: автоматическая оценка помогает быстро найти подозрительные места, но финальное решение принимает специалист. Если оценка кажется спорной, проверьте вопрос, ожидаемый ответ, критерии успеха и raw-ответ вручную.

## Локальный запуск

Локальный запуск нужен, если нужно проверить скрипт без Jenkins или быстро воспроизвести проблему.

Установите зависимости:

```bash
cd tester
pip install -r requirements.txt
```

Запустите тест:

```bash
python adk_agent_tester_v1.py --excel "C:\path\to\cases.xlsx" --out "C:\path\to\reports"
```

Полезные параметры:

| Параметр | Назначение |
| --- | --- |
| `--excel` | путь к Excel-файлу с тест-кейсами |
| `--out` | папка, куда сохранить отчет |
| `--user-id` | идентификатор тестового пользователя |
| `--session-id` | идентификатор тестовой сессии |
| `--fake-first-name` | тестовое имя пользователя для stateDelta |

Полный список параметров можно посмотреть командой:

```bash
python adk_agent_tester_v1.py --help
```

## Основные переменные окружения

| Переменная | Обязательность | Назначение |
| --- | --- | --- |
| `ADK_API_BASE` | обязательно | URL ADK Agent |
| `TC_TASK_FILE_NAME` | обязательно при запуске без `--excel` | имя Excel-файла с тест-кейсами |
| `LLM_API_KEY` | нужно для автооценки | ключ LLM-оценщика |
| `LLM_API_URL` | опционально | URL LLM API |
| `LLM_API_MODEL` | опционально | модель LLM-оценщика |
| `ADK_APP_NAME` | опционально | имя приложения в ADK, по умолчанию `agent` |
| `ADK_TIMEOUT_SEC` | опционально | таймаут HTTP-запросов к ADK |
| `ASK_QUESTIONS` | опционально | управляет отправкой вопросов агенту |
| `ADK_TEST_USER_ID`, `ADK_TEST_SESSION_ID` | опционально | тестовый пользователь и сессия |

## Частые ошибки

| Проблема | Что проверить |
| --- | --- |
| Jenkins job завершилась сразу после старта | загружен ли Excel-файл в `TC_TASK_FILE_LOCAL` |
| Скрипт не нашел входной файл | правильный ли путь в `--excel` или имя в `TC_TASK_FILE_NAME` |
| Агент недоступен | корректный ли `ADK_API_BASE`, работает ли нужное окружение |
| В отчете нет автооценки | задан ли `LLM_API_KEY` |
| Все оценки равны нулю | не была ли пропущена автооценка или не упал ли LLM-оценщик |
| Низкая оценка у корректного ответа | не слишком ли узко описаны `Ожидаемые ответы` и `Критерий успеха` |
| Один use case попал на несколько листов | одинаково ли написано значение `Use case` во всех строках группы |

## Критерий успешного запуска

Запуск можно считать успешным, если:

- Jenkins job завершилась без ошибки;
- появился файл `REPORT_*.xlsx`;
- в отчете есть лист `Итоги тестирования`;
- для каждого `Use case` есть детальный лист;
- в детальных листах заполнены ответы агента;
- при включенной автооценке заполнены оценки и объяснения.

После этого отчет можно использовать для анализа качества агента и планирования исправлений.
