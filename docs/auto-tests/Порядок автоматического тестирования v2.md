# Порядок автоматического тестирования v2

Эта инструкция описывает, как подготовить файл с проверками, запустить автоматическое тестирование через Jenkins и разобрать полученный отчет. Она рассчитана на исполнителя без технической подготовки.

## Когда использовать эту инструкцию

Используйте ее, когда нужно проверить, как чат-бот отвечает на набор заранее подготовленных вопросов.

В результате вы получите отчет, где будет видно:

- какие вопросы были заданы боту;
- что бот ответил;
- насколько ответ похож на ожидаемый;
- какие сценарии требуют внимания.

## Общая схема работы

1. Подготовить Excel-файл с тестовыми вопросами.
2. Загрузить этот файл в Jenkins.
3. Запустить проверку.
4. Скачать отчет.
5. Посмотреть проблемные ответы.
6. Передать выводы команде для исправления.

## Шаг 1. Подготовьте Excel-файл

Файл должен быть в формате `.xlsx`.

Одна строка в файле - это один вопрос для проверки.

В таблице должны быть такие колонки:

| Колонка | Что написать |
| --- | --- |
| `№` | номер вопроса |
| `Use case` | название группы проверок |
| `Вопросы` | вопрос, который будет задан боту |
| `Ожидаемые ответы` | какой ответ считается правильным |
| `Критерий успеха` | по каким признакам понятно, что ответ хороший |

Пример:

| № | Use case | Вопросы | Ожидаемые ответы | Критерий успеха |
| --- | --- | --- | --- | --- |
| 1 | `2-smalltalk` | `Привет` | Бот здоровается и предлагает помощь | Есть приветствие. Есть приглашение к диалогу |

## Как заполнять колонки

### `№`

Укажите порядковый номер вопроса.

Пример:

```text
1
2
3
```

### `Use case`

Укажите группу, к которой относится вопрос. Это нужно, чтобы потом в отчете видеть результат не только по каждому вопросу, но и по целому сценарию.

Примеры:

```text
1-устойчивость к взлому
2-smalltalk
3-kb_answer
4-doc_search
```

Если несколько вопросов проверяют один и тот же сценарий, пишите одинаковый `Use case`.

### `Вопросы`

Напишите вопрос так, как его мог бы задать пользователь.

Примеры:

```text
Привет
Что предложить клиенту, у которого деньги просто лежат?
В каких документах рассказывают про Fort Knox?
```

### `Ожидаемые ответы`

Опишите, что бот должен ответить. Не обязательно писать точную фразу слово в слово. Важно описать смысл правильного ответа.

Пример:

```text
Бот должен поздороваться, обратиться к пользователю и предложить помощь.
```

### `Критерий успеха`

Опишите признаки, по которым можно понять, что ответ правильный.

Лучше писать короткими пунктами.

Пример:

```text
1. Есть ответное приветствие.
2. Есть обращение по имени.
3. Есть приглашение к диалогу.
```

## Шаг 2. Проверьте файл перед запуском

Перед загрузкой в Jenkins проверьте:

- файл открывается в Excel;
- в файле есть все обязательные колонки;
- в колонке `Вопросы` нет пустых строк;
- названия `Use case` написаны одинаково для вопросов одной группы;
- в `Ожидаемые ответы` и `Критерий успеха` понятно, что именно нужно проверить.

Если критерии написаны слишком общо, отчет будет сложнее анализировать.

Плохой пример:

```text
Ответ хороший.
```

Хороший пример:

```text
1. Бот отвечает по теме вопроса.
2. Бот называет подходящие продукты.
3. Бот не придумывает факты, которых нет в материалах.
```

## Шаг 3. Запустите проверку в Jenkins

1. Откройте Jenkins job для автоматического тестирования.
2. Нажмите `Build with Parameters`.
3. В поле `TC_TASK_FILE_LOCAL` загрузите подготовленный Excel-файл.
4. Если есть выбор окружения, выберите нужное окружение для проверки.
5. Если есть выбор модели оценки, оставьте значение по умолчанию, если руководитель не сказал выбрать другое.
6. Нажмите кнопку запуска сборки.
7. Дождитесь завершения проверки.

Проверка может идти несколько минут. Чем больше вопросов в файле, тем дольше будет выполняться запуск.

## Шаг 4. Скачайте результаты

После завершения Jenkins job скачайте артефакты сборки.

Главный файл - отчет Excel:

```text
REPORT_*.xlsx
```

Также может быть файл с графиком:

```text
REPORT_*.png
```

или:

```text
REPORT_*.html
```

Для анализа в первую очередь нужен файл `REPORT_*.xlsx`.

## Шаг 5. Откройте отчет

В отчете есть два типа листов:

- `Итоги тестирования` - краткая сводка по группам вопросов;
- листы `Детали ...` - подробности по каждому вопросу внутри группы.

Начинайте с листа `Итоги тестирования`.

## Как читать лист `Итоги тестирования`

На этом листе каждая строка - это один `Use case`.

Основные колонки:

| Колонка | Что означает |
| --- | --- |
| `Код use case` | группа проверок |
| `Точность (сред)` | насколько ответы точны в среднем |
| `Полнота (сред)` | насколько полно бот отвечает |
| `Релевантность (сред)` | насколько ответ соответствует вопросу |
| `Соответствие всем критериям` | прошли ли все вопросы группы по критериям |
| `Общая оценка (сред)` | итоговая средняя оценка группы |

Сначала обращайте внимание на:

- низкую `Общая оценка (сред)`;
- значение `False` в колонке `Соответствие всем критериям`.

Именно эти группы нужно смотреть подробнее.

## Как читать листы `Детали ...`

На детальном листе каждая строка - это один вопрос.

Важные колонки:

| Колонка | Что смотреть |
| --- | --- |
| `Вопросы` | какой вопрос был задан |
| `Ожидаемые ответы` | какой ответ ожидался |
| `Критерий успеха` | по каким условиям ответ проверялся |
| `Ответ ADK Agent` | что фактически ответил бот |
| `Время ответа (сек)` | сколько секунд бот отвечал |
| `Общая оценка` | итоговая оценка ответа |
| `Объяснение` | почему выставлена такая оценка |

Если оценка низкая, сравните:

1. Что спросили в колонке `Вопросы`.
2. Что ожидали в колонке `Ожидаемые ответы`.
3. Какие условия указаны в `Критерий успеха`.
4. Что реально написал бот в `Ответ ADK Agent`.
5. Что написано в `Объяснение`.

## Как понять, что ответ проблемный

Ответ требует внимания, если:

- бот ответил не на тот вопрос;
- бот дал слишком общий ответ;
- бот пропустил важную часть ожидаемого ответа;
- бот добавил неподтвержденную информацию;
- бот не выполнил один или несколько критериев успеха;
- оценка низкая, а объяснение указывает на ошибку;
- ответ выглядит правильным, но критерий успеха не выполнен.

Иногда проблема может быть не в боте, а в самом тест-кейсе. Например, ожидаемый ответ слишком расплывчатый или критерий успеха написан неоднозначно.

## Шаг 6. Подготовьте выводы

После просмотра отчета подготовьте краткий список проблем.

Для каждой проблемы удобно фиксировать:

| Что указать | Пример |
| --- | --- |
| `Use case` | `3-kb_answer` |
| номер вопроса | `36` |
| вопрос | `Что предложить клиенту, у которого деньги просто лежат?` |
| что не так | бот предложил продукты, но не уточнил причину и риск-профиль клиента |
| что ожидалось | бот должен сначала предложить выяснить причину и риск-профиль |
| возможное действие | проверить базу знаний или логику выбора ответа |

Такой список можно передать аналитикам, разработчикам или ответственному за базу знаний.

## Рекомендации по анализу

- Не делайте вывод только по одной оценке: всегда смотрите сам ответ и объяснение.
- Если вопрос важный для бизнеса, проверьте его вручную особенно внимательно.
- Если несколько вопросов одного `Use case` провалились одинаково, скорее всего, проблема общая.
- Если провалился только один вопрос, возможно, нужно уточнить сам тест-кейс.
- Если ответ правильный, а оценка низкая, проверьте, достаточно ли ясно написаны ожидаемый ответ и критерии успеха.

## Короткий чек-лист

Перед запуском:

- Excel-файл подготовлен.
- Все обязательные колонки есть.
- Вопросы заполнены.
- Ожидаемые ответы понятны.
- Критерии успеха конкретные.

После запуска:

- Скачан `REPORT_*.xlsx`.
- Просмотрен лист `Итоги тестирования`.
- Проверены группы с низкими оценками.
- Просмотрены детальные листы.
- Составлен список проблем и предложений.
