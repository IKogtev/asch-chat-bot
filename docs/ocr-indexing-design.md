# Системное описание OCR-обогащения индекса для `kb_search` и `doc_search`

## 1. Назначение

Документ описывает целевое решение, при котором содержимое изображений и сканированных PDF становится доступно для поиска через существующие инструменты:

- `kb_search`;
- `doc_search`;
- агенты `kb_answer_agent`;
- агенты `doc_search_agent`.

Решение должно расширить текущую архитектуру без изменения пользовательского сценария скачивания документа: пользователю по-прежнему должен отдаваться исходный файл, а не OCR-артефакт.

---

## 2. Проблема

Существенная часть базы документов и базы знаний представлена:

- изображениями (`.png`, `.jpg`, `.jpeg`, `.tiff` и аналогичными форматами);
- сканированными PDF без извлекаемого текстового слоя;
- смешанными PDF, где часть страниц текстовые, а часть являются изображениями.

В текущем состоянии такие документы либо не попадают в индекс содержательно, либо попадают частично, из-за чего:

- `kb_search` не видит полезный текст;
- `doc_search` не находит релевантные документы;
- `kb_answer_agent` не может использовать знания из таких материалов;
- доля реально доступной для поиска базы заметно ниже доли фактически загруженных документов.

---

## 3. Цели

- Сделать OCR-текст доступным для поиска через существующий `kb_search`.
- Сохранить текущий контракт агентов и скачивания документов.
- Не создавать отдельный пользовательский инструмент поиска по OCR.
- Поддержать инкрементальную обработку новых и изменённых файлов.
- Избежать полной переиндексации всей базы при появлении одного нового скана.
- Сохранять связь OCR-данных с исходным документом на уровне `document_id`, `doc_hash` и `file_path`.

---

## 4. Не-цели

В рамках данного решения не планируется:

- заменять исходные файлы результатами OCR;
- отдавать OCR-текст пользователю вместо оригинала при скачивании;
- вводить отдельную коллекцию поиска только для OCR;
- строить новый пользовательский API поиска;
- решать задачу semantic post-processing OCR-текста через отдельный LLM-пайплайн;
- запускать OCR синхронно в пользовательском запросе поиска.

---

## 5. Текущее состояние системы

На момент подготовки документа в репозитории уже есть следующие элементы архитектуры:

- файловое хранилище документов и KB в `kb-manager`;
- дифф-синхронизация файловой системы и Qdrant в `FileStorageService.sync()`;
- подготовка чанков документов через `DocumentLoader`;
- семантический поиск в Qdrant через `mcp-server-kbsearch`;
- использование `document_id` и `file_path` для скачивания исходного документа;
- использование `kb_search` как общего поискового инструмента для `doc_search` и `kb_answer`.

Практически это означает:

- место для встраивания OCR есть в существующем пайплайне индексации;
- скачивание уже жёстко привязано к `file_path` из метаданных документа;
- контракт агентов лучше не менять, а расширять только внутреннюю подготовку данных.

---

## 6. Основная идея решения

Рекомендуемый подход:

1. Оригинальный файл остаётся единственным source of truth.
2. OCR работает как фоновое обогащение документа.
3. OCR-результат хранится как производный артефакт, а не как новый первичный документ.
4. В индекс попадают чанки OCR-текста, но они сохраняют ссылку на исходный `document_id`.
5. Поиск выполняется по объединённому индексу, а скачивание работает по исходному `file_path`.

Иными словами, OCR не создаёт отдельный документ для пользователя. Он создаёт дополнительный поисковый слой для уже существующего документа.

---

## 7. Архитектурные требования

### 7.1 Общие требования

- Решение должно быть идемпотентным.
- Решение должно быть совместимо с текущим Qdrant-подходом.
- Решение не должно ломать текущий сценарий `GET /api/documents/download/{document_id}`.
- Решение должно поддерживать повторную обработку документа при изменении файла.
- Решение должно поддерживать статусную модель обработки.

### 7.2 Требования к поиску

- `kb_search` должен искать по OCR-чанкам и по нативному тексту без изменений публичного контракта.
- Метаданные результата должны по-прежнему содержать `document_id`, `source`, `relative_path`, `file_path`.
- При поисковой выдаче один и тот же исходный документ не должен распадаться на “оригинал” и “OCR-двойник”.

### 7.3 Требования к качеству

- OCR не должен безусловно подменять качественный текстовый слой документа.
- Для плохих OCR-результатов должен существовать способ не включать их в индекс.
- Для PDF должно различаться состояние `text_pdf`, `scanned_pdf`, `mixed_pdf`.

---

## 8. Варианты реализации

## Вариант A. OCR как производный артефакт и общий индекс

Суть:

- OCR-результат хранится отдельно от оригинала;
- в Qdrant попадают OCR-чанки того же документа;
- у OCR-чанков тот же `document_id`, что и у исходного файла;
- скачивание остаётся неизменным.

Плюсы:

- минимально ломает текущую архитектуру;
- не требует нового search tool;
- не требует нового download flow;
- совместим с текущей логикой `doc_search` и `kb_answer`.

Минусы:

- нужно аккуратно управлять происхождением чанков;
- требуется расширение метаданных и логики синхронизации.

Это рекомендуемый вариант.

## Вариант B. Отдельная OCR-коллекция в Qdrant

Суть:

- OCR-данные индексируются в отдельную коллекцию;
- `kb_search` ищет в двух коллекциях и потом мержит результаты.

Плюсы:

- изоляция OCR-данных от основного индекса;
- можно независимо управлять экспериментами и качеством.

Минусы:

- выше сложность ранжирования и дедупликации;
- потребуется усложнение `kb_search`;
- выше риск дублей в выдаче;
- сложнее поддерживать единый `document_id`-контракт.

В рамках текущего проекта не рекомендуется.

## Вариант C. OCR как соседний `.txt` в файловой системе

Суть:

- рядом с `file.pdf` создаётся `file.ocr.txt`;
- дальнейшая индексация работает с ним как с обычным текстовым файлом.

Плюсы:

- быстро реализуется;
- концептуально просто.

Минусы:

- высокий риск рассинхронизации;
- неочевидный source of truth;
- сложнее отличать OCR от оригинального текста;
- повышенный риск дублей в индексе и в пользовательской логике.

Как постоянное решение не рекомендуется.

---

## 9. Выбранный вариант

Для реализации рекомендуется Вариант A:

- OCR-обогащение как фоновый производный слой;
- единый поисковый индекс;
- единый `document_id` исходного документа;
- неизменный download flow по оригинальному `file_path`.

---

## 10. Целевая архитектура

## 10.1 Компоненты

В решение входят следующие логические компоненты:

- `FileStorageService` как источник списка файлов и изменений;
- `DocumentLoader` как точка подготовки текстовых чанков;
- новый `OCR Enrichment Worker` как фоновый обработчик OCR;
- служебное хранилище OCR-артефактов;
- `QdrantService` и `Indexer` как слой индексации;
- `mcp-server-kbsearch` как существующий поисковый API;
- `doc_search_agent` и `kb_answer_agent` как потребители существующего `kb_search`.

## 10.2 Принцип работы

1. В файловом хранилище появляется новый или изменённый файл.
2. `FileStorageService.sync()` фиксирует изменение по `doc_hash`.
3. Для файлов, требующих OCR, создаётся или обновляется задание OCR.
4. OCR worker извлекает текст и сохраняет производный OCR-артефакт.
5. Индексатор формирует чанки с учётом:
   - нативного текста;
   - OCR-текста;
   - правил приоритета и дедупликации.
6. Чанки загружаются в Qdrant.
7. `kb_search` ищет по новому набору чанков без изменения публичного контракта.
8. При скачивании пользователю возвращается исходный файл по `file_path`.

---

## 11. Модель данных

## 11.1 Исходный документ

Для исходного документа сохраняются и используются текущие ключи:

- `document_id`;
- `doc_hash`;
- `file_path`;
- `relative_path`;
- `source`;
- `source_type`;
- `kb_id`;
- `section_path`.

## 11.2 OCR manifest

Для каждого документа, прошедшего OCR, должен существовать manifest со следующими полями:

- `document_id`;
- `doc_hash`;
- `kb_id`;
- `file_path`;
- `ocr_status`;
- `ocr_engine`;
- `ocr_engine_version`;
- `created_at`;
- `updated_at`;
- `page_count`;
- `pages`;
- `quality_score`;
- `error_code`;
- `error_message`.

`pages` содержит список страниц со структурой:

- `page_num`;
- `text`;
- `confidence`;
- `char_count`;
- `is_empty`;
- `needs_review`.

## 11.3 Метаданные чанка в Qdrant

В существующий payload рекомендуется добавить:

- `text_source`: `native` | `ocr` | `native+ocr`;
- `origin_document_id`;
- `origin_doc_hash`;
- `ocr_status`;
- `ocr_engine`;
- `ocr_confidence`;
- `page_num`;
- `extract_mode`;
- `is_ocr_fallback`.

При этом обязательно сохраняются:

- `document_id`;
- `file_path`;
- `relative_path`;
- `source`;
- `kb_id`.

`document_id` должен указывать на исходный документ, а не на отдельную OCR-сущность.

---

## 12. Хранилище OCR-артефактов

Рекомендуемая схема хранения:

```text
<kb_root>/_derived/ocr/<kb_id>/<doc_hash>/
  manifest.json
  page-0001.txt
  page-0002.txt
  ...
```

Требования к хранилищу:

- артефакты должны быть отделены от исходных файлов;
- путь должен быть детерминирован по `kb_id` и `doc_hash`;
- при изменении исходного файла старый OCR-артефакт считается устаревшим;
- OCR-артефакты не участвуют напрямую в пользовательском скачивании.

Причина выбора файлового хранения:

- текущая архитектура уже опирается на filesystem-first подход;
- ниже стоимость внедрения, чем у отдельной таблицы БД;
- проще отлаживать и пересобирать артефакты;
- не требуется миграция БД на первом этапе.

---

## 13. Статусы OCR-обработки

Для управления фоновым пайплайном вводится статусная модель:

- `pending` — документ обнаружен и ожидает OCR;
- `processing` — OCR выполняется;
- `done` — OCR завершён успешно;
- `failed` — OCR завершился ошибкой;
- `stale` — OCR-артефакт устарел, так как изменился `doc_hash`;
- `skipped` — OCR не требуется или качество слишком низкое для индексации.

Также требуется хранить:

- число попыток;
- время последней попытки;
- время следующего retry;
- код ошибки.

---

## 14. Классификация документов перед OCR

Перед OCR документ должен быть отнесён к одному из режимов:

- `native_text` — текст уже извлекается штатно;
- `ocr_required` — извлекаемого текста нет, нужен OCR;
- `mixed` — часть содержимого текстовая, часть требует OCR;
- `unsupported` — OCR не выполняется.

Правила высокого уровня:

- изображения почти всегда `ocr_required`;
- PDF с пустым или почти пустым текстовым слоем считаются `ocr_required`;
- PDF с частично извлекаемым текстом считаются `mixed`;
- обычные текстовые форматы OCR не требуют.

---

## 15. Логика подготовки текста к индексации

## 15.1 Базовые правила

- Если у документа есть качественный нативный текст, он остаётся основным источником.
- Если у документа нет пригодного текста, используется OCR.
- Для `mixed`-документов допускается объединение нативного и OCR-текста.
- Перед индексацией требуется дедупликация повторяющихся текстовых блоков.

## 15.2 Правила объединения

Для одного документа индексатор должен уметь:

- строить чанки только из native-текста;
- строить чанки только из OCR-текста;
- строить чанки из объединённого текста, если это повышает полноту без чрезмерного шума.

Практическое правило для первого этапа:

- если native-текст пустой, индексируется OCR;
- если native-текст непустой и выше порога качества, индексируется только native;
- если документ помечен как `mixed`, объединение выполняется постранично или поблочно с дедупликацией.

---

## 16. Встраивание в текущий пайплайн

## 16.1 `FileStorageService`

Текущий `FileStorageService.sync()` уже выполняет:

- обнаружение новых файлов;
- обнаружение изменённых файлов;
- удаление отсутствующих файлов из индекса;
- повторную индексацию при изменении.

В целевом решении он должен дополнительно:

- определять необходимость OCR;
- ставить задания в OCR backlog;
- помечать OCR-артефакты как `stale` при смене `doc_hash`;
- инициировать повторную индексацию после завершения OCR.

## 16.2 `DocumentLoader`

Текущий `DocumentLoader` подготавливает текст для индексации и уже задаёт метаданные:

- `document_id`;
- `doc_hash`;
- `content_hash`;
- `file_path`;
- `relative_path`.

В целевом решении он должен:

- уметь читать OCR manifest;
- решать, какой текст включать в индекс;
- добавлять расширенные метаданные происхождения текста;
- не создавать новый пользовательский документ для OCR.

## 16.3 `kb_search`

Текущий `kb_search` уже ищет по чанкам из Qdrant и возвращает:

- `content`;
- `metadata`;
- `document_id`;
- `relative_path`.

Менять его публичный контракт не требуется.

Допускается только внутренняя доработка:

- использовать новые метаданные;
- при необходимости мягко штрафовать noisy OCR при rerank;
- объединять результаты одного исходного документа без появления “второго OCR-документа”.

## 16.4 Download flow

Текущий download flow строится через:

- `document_id`;
- поиск чанков документа;
- `file_path` из метаданных;
- выдачу `FileResponse` по исходному файлу.

Это поведение должно быть сохранено без изменений.

---

## 17. Фоновая OCR-задача

## 17.1 Общий принцип

OCR должен выполняться асинхронно, вне пользовательского поискового запроса.

Причины:

- OCR может быть медленным;
- OCR может требовать повторов;
- OCR не должен увеличивать latency `kb_search`;
- поисковый API должен работать по уже готовому индексу.

## 17.2 Что делает worker

OCR worker периодически:

- сканирует backlog документов;
- выбирает документы со статусами `pending`, `stale`, `failed` с истёкшим retry;
- выполняет OCR;
- сохраняет manifest и page-text;
- инициирует индексирование или переиндексацию;
- фиксирует статус и метрики.

## 17.3 Режим запуска

На первом этапе допустим polling-подход:

- периодический проход по backlog;
- небольшой batch size;
- защита от параллельной двойной обработки одного документа.

На следующих этапах можно перейти на очередь задач, но это не обязательно для первого внедрения.

---

## 18. Правила повторной обработки

Документ должен идти на повторный OCR, если:

- изменился `doc_hash`;
- OCR-артефакт отсутствует;
- OCR завершился ошибкой и достигнут момент retry;
- изменился OCR engine или его версия, и принято решение о массовом reprocess.

Документ не должен идти на OCR повторно, если:

- `doc_hash` совпадает;
- manifest актуален;
- статус `done`;
- политика reprocess не требует обновления.

---

## 19. Дедупликация и предотвращение дублей

Для предотвращения дублей требуется:

- единый `document_id` для исходного документа и OCR-чанков;
- раздельные `chunk_id` для разных чанков;
- использование `content_hash` для защиты от повторной загрузки одинаковых чанков;
- дедупликация native и OCR-текста при `mixed`-режиме.

Отдельно важно:

- нельзя индексировать один и тот же текст дважды только из-за того, что он пришёл из двух источников;
- нельзя выводить пользователю два документа, если это один исходный файл с двумя источниками текста.

---

## 20. Качество OCR и фильтрация шума

Без quality gate OCR-слой может засорить поиск.

Поэтому должны существовать базовые фильтры:

- не индексировать пустые страницы;
- не индексировать страницы с очень низким количеством буквенно-цифровых символов;
- не индексировать OCR с экстремально низким confidence;
- по возможности убирать повторяющиеся штампы и служебные колонтитулы.

Дополнительно рекомендуется:

- логировать долю пустых OCR-страниц;
- логировать документы с подозрительно низким качеством OCR;
- позволять отключать индексацию плохих OCR-результатов.

---

## 21. Наблюдаемость и эксплуатация

Для решения должны быть доступны:

- счётчик документов в OCR backlog;
- число успешно обработанных документов;
- число документов с ошибкой;
- среднее время OCR на документ;
- среднее время OCR на страницу;
- доля документов, searchable только через OCR;
- доля документов, для которых OCR дал пустой результат.

Также нужны диагностические возможности:

- посмотреть OCR manifest по `document_id`;
- понять, почему документ не попал в OCR;
- понять, по какому источнику текста был построен индекс.

---

## 22. Риски

## 22.1 Технические риски

- шумный OCR может ухудшить релевантность поиска;
- смешивание native и OCR без правил приведёт к дублям;
- отсутствие статусов приведёт к зацикленным ретраям;
- отсутствие привязки к `doc_hash` приведёт к устаревшему OCR;
- синхронный OCR в upload flow ухудшит UX и стабильность.

## 22.2 Архитектурные риски

- отдельная OCR-коллекция усложнит `kb_search`;
- хранение `.ocr.txt` рядом с файлами создаст рассинхрон;
- новый пользовательский инструмент поиска по OCR создаст ненужное раздвоение сценариев.

## 22.3 Эксплуатационные риски

- накопление backlog при большом потоке документов;
- рост затрат на OCR;
- рост размера индекса и времени переиндексации;
- отсутствие метрик затруднит поддержку.

---

## 23. Ограничения первого этапа

Для первого этапа рекомендуется ограничить объём решения:

- поддержать OCR только для изображений и сканированных PDF;
- не менять публичный API поиска;
- не менять download API;
- не вводить отдельную БД для OCR manifest;
- не внедрять сложный page-layout analysis;
- не выполнять LLM-постобработку OCR как обязательную часть пайплайна.

Это позволит решить основную проблему без избыточной сложности.

---

## 24. Этапы внедрения

## Этап 1. Базовый контур OCR enrichment

- Добавить модель OCR manifest.
- Добавить файловое хранилище `_derived/ocr`.
- Добавить OCR worker с polling/backlog-подходом.
- Добавить классификацию `native_text` / `ocr_required` / `mixed`.

Результат этапа:

- система умеет распознавать новые изображения и scanned PDF;
- OCR-артефакты сохраняются отдельно;
- есть статусы обработки.

## Этап 2. Интеграция с индексацией

- Расширить `DocumentLoader`.
- Добавить новые поля метаданных чанков.
- Обновить логику переиндексации по `doc_hash` и OCR status.
- Обеспечить сохранение `document_id` исходного документа.

Результат этапа:

- OCR-данные попадают в Qdrant;
- `kb_search` начинает находить текст из OCR.

## Этап 3. Управление качеством

- Добавить quality gate для OCR.
- Добавить базовую дедупликацию native/OCR.
- Добавить метрики и диагностические endpoint или debug-функции.

Результат этапа:

- поиск не деградирует из-за массового OCR-шумa;
- команда может наблюдать состояние OCR-контура.

## Этап 4. Улучшение mixed PDF

- Добавить объединение native и OCR по страницам.
- Уточнить правила rerank для OCR-контента.
- Снизить дубли и шум в поисковой выдаче.

Результат этапа:

- mixed PDF полноценно участвуют в поиске;
- выдача становится стабильнее и релевантнее.

---

## 25. Критерии готовности

Решение можно считать готовым к эксплуатации, если:

- новый image/scanned PDF документ автоматически попадает в OCR backlog;
- после фоновой обработки текст документа становится доступен через `kb_search`;
- `doc_search` и `kb_answer` используют этот текст без изменения своего внешнего контракта;
- скачивание по `document_id` возвращает исходный файл;
- изменение исходного файла приводит к инвалидированию старого OCR;
- в системе есть наблюдаемые статусы и метрики обработки.

---

## 26. Рекомендуемое решение для реализации

Для команды разработки рекомендуется принять следующее решение:

- реализовать OCR как фоновое обогащение существующего индекса;
- хранить OCR как производный артефакт, а не как соседний пользовательский файл;
- индексировать OCR-чанки в тот же логический индекс Qdrant;
- сохранять единый `document_id` исходного документа;
- оставить `kb_search`, `doc_search` и download flow без изменения публичного контракта.

Это решение лучше всего соответствует текущей архитектуре репозитория и даёт наименьшую стоимость внедрения при максимальном практическом эффекте.
