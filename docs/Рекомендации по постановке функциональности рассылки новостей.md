# Рекомендации по постановке функциональности рассылки новостей

Нормальная постановка здесь такая: не просто «рассылка новостей», а **подсистема кампаний/новостей** внутри административного UI и backend.

Это лучше ложится на текущую архитектуру: есть `bot`, `adk-agent`, `postgres`, `kbsearch`, `mcp-filesystem`. Значит рассылку лучше делать как отдельный прикладной контур внутри backend, а не пытаться встраивать ее в AI-agent.

## 1. Цель

Система должна позволять администратору:

- создавать новости;
- редактировать новости;
- планировать отправку;
- отправлять новости пользователям Telegram-бота;
- выбирать группы получателей;
- прикладывать вложения;
- использовать старые новости как основу;
- автоматически формировать черновик новости по изменениям в папке «Презентеры».

## 2. Общий подход

Функциональность лучше описывать как **подсистему новостей и рассылок**.

В состав подсистемы входят:

- вкладка в UI;
- backend API для управления новостями;
- таблицы БД для пользователей, групп, новостей и истории отправок;
- планировщик/воркер для отправки по времени;
- модуль подготовки черновиков по обновленным документам.

## 3. Роли

### Администратор рассылки
Работает во вкладке UI:
- создает новости;
- редактирует;
- прикладывает вложения;
- задает группы получателей;
- запускает отправку;
- просматривает историю.

### Получатель
Пользователь Telegram-бота, который получает новости.

### Система
Автоматически:
- отправляет новости по расписанию;
- формирует черновики по обновлениям в папке «Презентеры».

## 4. Что должно быть в UI

Новая вкладка: **«Новости / Рассылки»**.

Внутри вкладки:

### Список новостей
- список всех новостей;
- фильтры по статусам;
- поиск;
- сортировка по дате создания / дате отправки.

### Статусы
- `draft`
- `scheduled`
- `sending`
- `sent`
- `partially_sent`
- `failed`
- `cancelled`

### Форма новости
Поля:

- заголовок;
- внутреннее имя / код;
- текст новости;
- формат текста;
- дата и время отправки;
- группы получателей;
- вложения;
- комментарий/служебная заметка;
- источник (если создана на основе старой);
- предпросмотр.

Кнопки:

- «Сохранить как черновик»
- «Отправить сейчас»
- «Запланировать»
- «Отправить тестово»
- «Создать на основе старой»

### История
Для каждой новости:
- кто создал;
- когда создал;
- когда отправил;
- на какие группы была отправка;
- сколько пользователей получили;
- сколько ошибок;
- детализация ошибок.

## 5. Пользователи

Сейчас пользователей надо хранить не только как историю сообщений, а как отдельную сущность в БД.

Нужна таблица `users`.

Минимальные поля:

- `id`
- `telegram_user_id`
- `username`
- `first_name`
- `last_name`
- `is_active`
- `is_blocked`
- `last_seen_at`
- `created_at`
- `updated_at`

### Логика наполнения
Пользователь должен сохраняться или обновляться:
- при `/start`;
- при любом входящем сообщении;
- при любом контакте с ботом.

Это нужно для того, чтобы база получателей формировалась автоматически.

## 6. Группы пользователей

Нужны отдельные группы получателей.

На первом этапе:
- `managers`
- `coaches`

Лучше хранить группы как справочник, а не зашивать жестко в код.

Нужны таблицы:
- `user_groups`
- `user_group_membership`

Это даст возможность потом:
- добавлять новые группы;
- назначать одного пользователя в несколько групп;
- фильтровать рассылки по нужным сегментам.

## 7. Форматирование новости

Здесь надо принять одно решение и зафиксировать его.

Рекомендация: **использовать HTML**, а не Markdown.

### Почему HTML лучше для Telegram
- проще контролировать форматирование;
- меньше проблем с экранированием спецсимволов;
- меньше риск сломать сообщение из-за синтаксиса;
- удобнее валидировать на backend.

Поэтому в постановке лучше прямо зафиксировать:

> Текст новости хранится и отправляется в формате HTML, совместимом с Telegram Bot API.

## 8. Вложения

Нужно поддержать вложения к новости.

Возможные типы:
- документы;
- PDF;
- изображения;
- презентации;
- другие разрешенные файлы.

### Что нужно предусмотреть
- загрузка файла через UI;
- хранение метаданных вложения в БД;
- физическое хранение файла;
- привязка вложений к новости;
- ограничения по размеру и типам;
- журнал ошибок отправки вложений.

### Важно разделить
Надо различать:

1. **Файл-вложение**, который реально отправляется в Telegram;
2. **Ссылку на документ**, которая просто вставляется в текст новости.

Это разные сущности, лучше не смешивать.

## 9. Отправка новости

Должны быть два режима:

### Отправить сейчас
Администратор нажимает кнопку, система сразу запускает отправку.

### Запланировать отправку
Администратор задает дату/время, система сама отправляет позже.

## 10. Планировщик

Отправка по времени должна выполняться не из UI и не через AI-agent, а отдельным backend-воркером.

### Логика планировщика
Периодически:
- берет новости со статусом `scheduled`;
- проверяет `scheduled_at <= now`;
- переводит в `sending`;
- собирает список пользователей по группам;
- отправляет сообщения;
- пишет результат в историю доставки;
- выставляет итоговый статус.

### Важные требования
- защита от повторной отправки;
- идемпотентность;
- устойчивость к падению сервиса;
- логирование ошибок по каждому пользователю;
- повторные попытки там, где это допустимо.

## 11. История новостей

Нужно хранить историю новостей и историю доставки.

### История новости
- текст;
- заголовок;
- формат;
- вложения;
- группы получателей;
- кто создал;
- кто изменил;
- когда отправили;
- итоговый статус.

### История доставки
Для каждого получателя:
- `news_id`
- `user_id`
- статус доставки
- дата/время попытки
- текст ошибки
- число попыток

Это позволит:
- видеть реальные результаты отправки;
- разбирать ошибки;
- делать повторную отправку при необходимости.

## 12. Создание новости на основе старой

Это полезная функция, ее надо явно включить в постановку.

### Как должно работать
Администратор выбирает старую новость и нажимает:
- «Создать на основе старой»

Система создает новый `draft`, в который копируются:
- заголовок или его шаблон;
- текст;
- формат;
- группы;
- вложения или ссылки на них;
- структура сообщения.

При этом новая новость не должна быть автоматически запланирована или отправлена.

## 13. Автогенерация новости по папке «Презентеры»

Это отдельный сценарий, его лучше описать как полуавтоматический процесс.

### Исходные данные
Есть папка **«Презентеры»**, путь к которой задается в настройках.

### Что делает система
Система должна:
- отслеживать изменения в этой папке;
- определять документы, обновленные с момента последней информирующей рассылки;
- собирать список измененных документов;
- создавать черновик новости.

### Что должно входить в черновик
Шаблон примерно такой:

> За последний период с `<дата>` по `<дата>` были обновлены следующие материалы:

Дальше таблица:
- имя документа;
- путь / раздел;
- дата изменения;
- комментарий или тип документа — если доступно.

### Важный момент
Лучше **создавать черновик**, а не отправлять автоматически.

То есть поток должен быть таким:
1. Система нашла изменения;
2. Сформировала заготовку;
3. Администратор открыл;
4. Проверил/отредактировал;
5. Отправил вручную или запланировал.

Это безопаснее и удобнее.

## 14. Настройки

Нужен отдельный блок настроек подсистемы.

Минимум:
- путь к папке «Презентеры»;
- формат новостей;
- лимиты по вложениям;
- кто имеет доступ к вкладке;
- пользователь/чат для тестовой отправки;
- периодичность проверки обновлений папки;
- шаблон автогенерируемой новости.

## 15. Что не надо делать

Не стоит:
- строить рассылку через AI-agent;
- хранить новости в истории чата;
- делать отправку непосредственно из UI без backend-очереди;
- делать автоматическую отправку по обновленным документам без проверки человеком;
- жестко вшивать группы в интерфейс и код без справочника.

## 16. Предлагаемая структура сущностей

Минимально нужны такие сущности:

- `users`
- `user_groups`
- `user_group_membership`
- `news_items`
- `news_attachments`
- `news_target_groups`
- `news_delivery`
- `news_templates`
- `folder_watch_state`
- `generated_news_drafts`

## 17. Декомпозиция по этапам

### Этап 1. База и пользователи
- таблицы пользователей;
- таблицы групп;
- membership;
- обновление пользователей при сообщениях боту.

### Этап 2. Новости
- CRUD новостей;
- черновики;
- статусы;
- вложения;
- выбор групп.

### Этап 3. Ручная отправка
- отправка сейчас;
- отправка в тестовый чат;
- лог результата.

### Этап 4. Планирование
- `scheduled_at`;
- backend scheduler;
- защита от дублей;
- retries;
- финальные статусы.

### Этап 5. История и переиспользование
- журнал отправок;
- детализация по пользователям;
- создание новости на основе старой.

### Этап 6. Папка «Презентеры»
- настройка пути;
- сканирование изменений;
- определение периода;
- генерация черновика по шаблону.

## 18. Нефункциональные требования

Обязательно стоит прописать:

- массовая отправка должна идти батчами;
- нужно учитывать rate limit Telegram;
- ошибки одного пользователя не должны ронять всю рассылку;
- должна быть защита от повторной массовой отправки;
- нужен аудит действий администратора;
- нужна тестовая отправка;
- нужна возможность предпросмотра;
- нужна возможность остановки еще не начатой рассылки;
- нужны понятные логи и статусы.

## 19. Рекомендуемая итоговая формулировка постановки

> Требуется реализовать подсистему новостных рассылок в административном UI Telegram-бота.  
> Подсистема должна обеспечивать создание, редактирование, хранение, планирование и отправку новостей пользователям бота.
>
> Система должна хранить пользователей в PostgreSQL как отдельные сущности, поддерживать пользовательские группы (на первом этапе: менеджеры и коучи), позволять выбирать целевые группы при подготовке новости, прикладывать вложения, задавать дату и время отправки, выполнять отправку немедленно или по расписанию, а также хранить историю всех новостей и результатов доставки.
>
> Новость должна поддерживать форматирование текста в формате HTML, предпросмотр и тестовую отправку.  
> Должна быть возможность создать новую новость на основе ранее отправленной или сохраненной.
>
> Также требуется реализовать сценарий автогенерации черновика новости по изменениям в папке «Презентеры»: путь к папке задается в настройках, система определяет документы, измененные с момента последней успешной информирующей рассылки, и формирует черновик новости с указанием периода и таблицей измененных документов.
>
> Отправка должна выполняться backend-воркером с логированием, защитой от повторной отправки и сохранением статуса доставки по каждому получателю.

## 20. Итоговое архитектурное решение

Лучшее решение для вашего проекта:

- **UI-вкладка** для работы администратора;
- **таблицы PostgreSQL** для пользователей, групп, новостей и доставки;
- **backend API** для CRUD и запуска отправок;
- **scheduler/worker** для запланированных рассылок;
- **интеграция с Telegram Bot API** для доставки;
- **модуль сканирования папки «Презентеры»** для подготовки черновиков.

Итог: это должен быть **обычный production-модуль рассылок**, а не функциональность, завязанная на агента.
