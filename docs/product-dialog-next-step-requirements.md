# Требования к предложению следующего шага в диалоге

## Цель

После содержательных ответов бот должен мягко предлагать пользователю следующий полезный шаг и уметь обрабатывать короткий ответ на это предложение. Основной сценарий должен вести пользователя по цепочке:

1. фильтр свойств продуктов, например доступные валюты;
2. фильтр продуктов, например список продуктов в долларах;
3. карточка выбранного продукта;
4. скачивание комплекта документов.

Цепочка не является обязательной: пользователь в любой момент может задать другой продуктовый вопрос, FAQ-вопрос или запросить документы через `doc_search`.

## Текущая реализация, которую нужно сохранить

- Основная маршрутизация уже находится в `RootAgent`: `owasp_agent` -> `dispatcher_agent` -> `doc_search`, `kb_answer` или `product_selection`.
- Продуктовые сценарии уже имеют явные intent/mode: `product_attribute_values`, `product_filter`, `product_card`, `product_kit`, `product_compare`, `needs_clarification`, `no_data`.
- `RootAgent` уже хранит `_product_dialog_context` после списков значений, списков продуктов, карточки и комплекта.
- Для продуктовых списков и карточек уже добавляются follow-up предложения в `_format_product_selection_answer`.
- Короткие продуктовые follow-up уже частично обрабатываются в `_product_followup_dispatch`: значение свойства, код продукта, запрос карточки или комплекта по выбранному продукту.
- Скачивание комплекта продукта уже выполняется через структурное действие `_bot_action` с `type="send_product_kit"`.
- Для `doc_search` уже есть отдельная механика коротких команд: `ещё`, `все`, номера документов для скачивания. Ее не нужно смешивать с продуктовой цепочкой.

## Функциональные требования

1. Каждый успешный пользовательский результат должен содержать один короткий следующий шаг, если такой шаг уместен.
2. Предложение должно быть полезным, не рекламным: без давления, без обещаний сверх данных, без повторения длинных инструкций.
3. Предложение должно соответствовать текущему mode:
   - `product_attribute_values`: предложить выбрать значение свойства для фильтра продуктов;
   - `product_filter`: предложить показать карточку продукта из списка;
   - `product_card`: предложить скачать комплект документов по этому продукту;
   - `product_kit`: после отправки комплекта не навязывать новый шаг, максимум коротко предложить задать вопрос по продукту;
   - `doc_search`: сохранить текущие подсказки про `ещё`, `все`, номер документа;
   - `kb_answer`: не вести насильно в продуктовую цепочку, если вопрос не продуктовый.
4. Короткий ответ пользователя должен интерпретироваться через последнее сохраненное предложение:
   - `да` выполняет предложенное действие только если оно однозначно;
   - если предложение неоднозначно, например в списке несколько продуктов, `да` должно приводить к уточняющему вопросу, а не к выбору продукта наугад;
   - код продукта из предыдущего списка открывает карточку этого продукта;
   - значение свойства из предыдущего списка запускает новый `product_filter`;
   - `комплект`, `скачать`, `пришли документы` после карточки запускают `product_kit` по выбранному продукту.
5. Если пользователь задает новый вопрос, он должен маршрутизироваться как новый запрос. Последнее предложение не должно перехватывать явные FAQ, `doc_search`, сравнение, новый фильтр или другой продукт.
6. Если запрос непонятен или короткий ответ невозможно безопасно связать с последним предложением, бот должен задать уточняющий вопрос.
7. Точность ответов важнее продвижения по цепочке: факты по продуктам остаются только из текущего `execute_sql`, документы только из `doc_search`/комплектов, FAQ только из `faq_search`/`kb_search`.
8. Тон ответов должен быть теплым и деловым: "Могу показать...", "Если удобно, напишите...", "Подскажу..." вместо рекламных формулировок.

## Критерии приемки

- После запроса "в каких валютах есть продукты" бот показывает значения и предлагает выбрать валюту.
- После ответа "доллары" или "USD" бот показывает список продуктов с этим свойством.
- После списка из одного продукта ответ "да" открывает карточку продукта, если последнее предложение было про карточку.
- После списка из нескольких продуктов ответ "да" не выбирает случайный продукт, а просит указать код или название.
- После карточки продукта ответ "да", "комплект" или "скачать" запускает отправку комплекта документов по этому продукту.
- Если после карточки пользователь спрашивает FAQ или ищет документы, запрос уходит в `kb_answer` или `doc_search`, а не в `product_kit`.
- При неоднозначном продукте используется существующий `needs_clarification`.
- Существующие команды `ещё`, `все`, номера документов для `doc_search` не ломаются.

## Предлагаемый способ решения

Минимальное системное решение - развить существующий `_product_dialog_context`, а не добавлять отдельный диалоговый движок.

1. Добавить в `_product_dialog_context` поле последнего предложения:
   - `last_offer`: `filter_by_attribute`, `show_product_card`, `send_product_kit`, `ask_product_question`;
   - `default_product`: только если действие однозначно;
   - `allowed_short_replies`: например `["да"]`, `["да", "комплект", "скачать"]`;
   - `clarification_prompt`: текст для случая, когда короткий ответ неоднозначен.
2. Вынести добавление следующего шага в отдельный helper в `RootAgent`, например `_append_next_step_offer(product_selection, context)`. Он должен использовать mode и данные результата, а не давать продуктовые факты самостоятельно.
3. Расширить `_product_followup_dispatch`:
   - сначала проверять явные новые намерения и не перехватывать их;
   - затем обрабатывать `да` только по `last_offer`;
   - при неоднозначности возвращать безопасный уточняющий ответ через `needs_clarification`-подобный текст или отдельный `_root_final_text`, без вызова продуктового SQL;
   - для однозначного `show_product_card` формировать search_query с кодом продукта;
   - для однозначного `send_product_kit` формировать search_query на комплект по коду продукта.
4. Оставить строгие правила `product_selection_agent`: карточка и комплект не могут строиться из истории, `_product_dialog_context` используется только для понимания выбора пользователя и формирования нового запроса.
5. Скорректировать промпт `product_selection_agent` только в части тона и финальных предложений. Не менять SQL-правила, обязательный `execute_sql` и запрет фактов из памяти.
6. При необходимости уточнить `dispatcher_agent_prompt`: явные FAQ/doc_search/product запросы имеют приоритет над коротким follow-up, если сообщение содержит новую содержательную тему.
7. Добавить unit-тесты в `tests/unit/agent/test_rootagent.py`:
   - `да` после списка из одного продукта -> `product_card`;
   - `да` после списка из нескольких продуктов -> уточнение;
   - `да` после карточки -> `product_kit`;
   - FAQ/doc_search после продуктового предложения не перехватывается;
   - существующие `doc_search` follow-up остаются без изменений.

## Риски и ограничения

- Нельзя делать `да` универсальной командой: без сохраненного `last_offer` или при неоднозначном контексте это должно быть уточнение.
- Нельзя выбирать первый продукт из длинного списка только потому, что пользователь ответил `да`.
- Нельзя добавлять продающие формулировки в промпт так, чтобы они ухудшали точность или заставляли агента отвечать без данных.
- Нельзя объединять продуктовые follow-up с follow-up документов: у них разные источники состояния и разные обработчики.
