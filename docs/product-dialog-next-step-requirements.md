# Требования к предложению следующего шага в диалоге

## Цель

После содержательных ответов бот должен мягко предлагать пользователю следующий полезный шаг и уметь обрабатывать короткий ответ на это предложение. Основной сценарий должен вести пользователя по цепочке:

1. фильтр свойств продуктов, например доступные валюты;
2. фильтр продуктов, например список продуктов в долларах;
3. карточка выбранного продукта;
4. скачивание комплекта документов.

Цепочка не является обязательной: пользователь в любой момент может задать другой продуктовый вопрос, FAQ-вопрос или запросить документы через `doc_search`.

## Текущая реализация, которую нужно сохранить

- Основная маршрутизация уже находится в `RootAgent`: `owasp_agent` -> `dispatcher_agent` -> `doc_search`, `kb_answer` или `product_selection`.
- Продуктовые сценарии уже имеют явные intent/mode: `product_attribute_values`, `product_filter`, `product_card`, `product_kit`, `product_compare`, `needs_clarification`, `no_data`.
- `RootAgent` уже хранит `_product_dialog_context` после списков значений, списков продуктов, карточки и комплекта.
- Для продуктовых списков и карточек уже добавляются follow-up предложения в `_format_product_selection_answer`.
- Короткие продуктовые follow-up уже частично обрабатываются в `_product_followup_dispatch`: значение свойства, код продукта, запрос карточки или комплекта по выбранному продукту.
- Скачивание комплекта продукта уже выполняется через структурное действие `_bot_action` с `type="send_product_kit"`.
- Для `doc_search` уже есть отдельная механика коротких команд: `ещё`, `все`, номера документов для скачивания. Ее не нужно смешивать с продуктовой цепочкой.

## Функциональные требования

1. Каждый успешный пользовательский результат должен содержать один короткий следующий шаг, если такой шаг уместен.
2. Предложение должно быть полезным, не рекламным: без давления, без обещаний сверх данных, без повторения длинных инструкций.
3. Предложение должно соответствовать текущему mode:
   - `product_attribute_values`: предложить выбрать значение свойства для фильтра продуктов;
   - `product_filter`: предложить показать карточку продукта из списка;
   - `product_card`: предложить скачать комплект документов по этому продукту;
   - `product_kit`: после отправки комплекта не навязывать новый шаг, максимум коротко предложить задать вопрос по продукту;
   - `doc_search`: сохранить текущие подсказки про `ещё`, `все`, номер документа;
   - `kb_answer`: не вести насильно в продуктовую цепочку, если вопрос не продуктовый.
4. Короткий ответ пользователя должен интерпретироваться через последнее сохраненное предложение:
   - `да` выполняет предложенное действие только если оно однозначно;
   - если предложение неоднозначно, например в списке несколько продуктов, `да` должно приводить к уточняющему вопросу, а не к выбору продукта наугад;
   - код продукта из предыдущего списка открывает карточку этого продукта;
   - значение свойства из предыдущего списка запускает новый `product_filter`;
   - `комплект`, `скачать`, `пришли документы` после карточки запускают `product_kit` по выбранному продукту.
5. Если пользователь задает новый вопрос, он должен маршрутизироваться как новый запрос. Последнее предложение не должно перехватывать явные FAQ, `doc_search`, сравнение, новый фильтр или другой продукт.
6. Если запрос непонятен или короткий ответ невозможно безопасно связать с последним предложением, бот должен задать уточняющий вопрос.
7. Точность ответов важнее продвижения по цепочке: факты по продуктам остаются только из текущего `execute_sql`, документы только из `doc_search`/комплектов, FAQ только из `faq_search`/`kb_search`.
8. Тон ответов должен быть теплым и деловым: "Могу показать...", "Если удобно, напишите...", "Подскажу..." вместо рекламных формулировок.

## Критерии приемки

- После запроса "в каких валютах есть продукты" бот показывает значения и предлагает выбрать валюту.
- После ответа "доллары" или "USD" бот показывает список продуктов с этим свойством.
- После списка из одного продукта ответ "да" открывает карточку продукта, если последнее предложение было про карточку.
- После списка из нескольких продуктов ответ "да" не выбирает случайный продукт, а просит указать код или название.
- После карточки продукта ответ "да", "комплект" или "скачать" запускает отправку комплекта документов по этому продукту.
- Если после карточки пользователь спрашивает FAQ или ищет документы, запрос уходит в `kb_answer` или `doc_search`, а не в `product_kit`.
- При неоднозначном продукте используется существующий `needs_clarification`.
- Существующие команды `ещё`, `все`, номера документов для `doc_search` не ломаются.
- Команда `3` или `1,3` после списка документов скачивает файл по номеру; без активного doc-list контекста такие короткие числа не перехватываются как скачивание.
- Команды `ещё` / `все` после списка документов продолжают или раскрывают список только при `last_route=doc_search` и непустом `last_document_list`.
- Фразы вроде «скачай его» без номера не считаются doc-list follow-up и уходят в обычную маршрутизацию, если не перехватываются другими follow-up.

## Предлагаемый способ решения

Минимальное системное решение - развить существующий `_product_dialog_context`, а не добавлять отдельный диалоговый движок.

1. Добавить в `_product_dialog_context` поле последнего предложения:
   - `last_offer`: `filter_by_attribute`, `show_product_card`, `send_product_kit`, `ask_product_question`;
   - `default_product`: только если действие однозначно;
   - `allowed_short_replies`: например `["да"]`, `["да", "комплект", "скачать"]`;
   - `clarification_prompt`: текст для случая, когда короткий ответ неоднозначен.
2. Вынести добавление следующего шага в отдельный helper в `RootAgent`, например `_append_next_step_offer(product_selection, context)`. Он должен использовать mode и данные результата, а не давать продуктовые факты самостоятельно.
3. Расширить `_product_followup_dispatch`:
   - сначала проверять явные новые намерения и не перехватывать их;
   - затем обрабатывать `да` только по `last_offer`;
   - при неоднозначности возвращать безопасный уточняющий ответ через `needs_clarification`-подобный текст или отдельный `_root_final_text`, без вызова продуктового SQL;
   - для однозначного `show_product_card` формировать search_query с кодом продукта;
   - для однозначного `send_product_kit` формировать search_query на комплект по коду продукта.
4. Оставить строгие правила `product_selection_agent`: карточка и комплект не могут строиться из истории, `_product_dialog_context` используется только для понимания выбора пользователя и формирования нового запроса.
5. Скорректировать промпт `product_selection_agent` только в части тона и финальных предложений. Не менять SQL-правила, обязательный `execute_sql` и запрет фактов из памяти.
6. При необходимости уточнить `dispatcher_agent_prompt`: явные FAQ/doc_search/product запросы имеют приоритет над коротким follow-up, если сообщение содержит новую содержательную тему.
7. Добавить unit-тесты в `tests/unit/agent/test_rootagent.py`:
   - `да` после списка из одного продукта -> `product_card`;
   - `да` после списка из нескольких продуктов -> уточнение;
   - `да` после карточки -> `product_kit`;
   - FAQ/doc_search после продуктового предложения не перехватывается;
   - doc-list follow-up срабатывает только при активном контексте списка;
   - `3` без контекста не уходит в `file_download`;
   - `ещё` / `все` / `3` с контекстом обходят dispatcher и формируют `_bot_action`.

## Риски и ограничения

- Нельзя делать `да` универсальной командой: без сохраненного `last_offer` или при неоднозначном контексте это должно быть уточнение.
- Нельзя выбирать первый продукт из длинного списка только потому, что пользователь ответил `да`.
- Нельзя добавлять продающие формулировки в промпт так, чтобы они ухудшали точность или заставляли агента отвечать без данных.
- Нельзя объединять продуктовые follow-up с follow-up документов: у них разные источники состояния и разные обработчики.
- Doc-list follow-up не должен срабатывать без gate (`last_route=doc_search` + `last_document_list`): иначе короткие числа и «ещё» будут перехватываться вне сценария списка.
- Generic-фразы («скачай его») без номера не должны молча скачивать первый документ — только явный rank или обычная маршрутизация.



# Статус реализации тикетов по диалоговому контексту
Цель изменений

Основная цель изменений — обеспечить устойчивое ведение многошагового диалога без потери контекста между репликами пользователя.
С сохранением последних 3 сообщений для контекста в виде очереди. 

Ранее rootagent каждый запрос в основном рассматривался изолировано, несмотря на наличие ограниченной истории сообщений и _product_dialog_context, система не сохраняла достаточное количество информации для корректной обработки коротких follow-up запросов вида: 
- "первый";
- "его";
- "что дальше";
- "открой файл";
- "расскажи про него";
- "дай комплект";
- "сравни его с ..."
Из-за этого происходил повторный поиск либо выбирался неверный маршрут обработки.

В новой реализации (rootagent.py) механизм хранения состояния был существенно расширен.

# Что уже реализовано
## 1. Расширенное хранение состояния диалога
помимо существующего `_product_dialog_context` теперь сохраняются отдельные пары состояния:
- last_user_query
- last_route
- last_intent
- last_search_query
- last_product
- last_document_list
Эти поля автоматически обновляются после каждого успешного ответа агента.

Это позволяет последующим репликам понимать:

какой маршрут выполнялся ранее;
какой продукт обсуждался;
какие документы были найдены;
какой поисковый запрос использовался.

## 2. Автоматическое восстановление продукта после поиска документов
Ранее после поиска документов происходила потеря связи между найденными файлами и продуктом.

Теперь после успешного doc_search:

- автоматически извлекается код продукта;
- определяется название продукта;
- сохраняется last_product;
- обновляется _product_dialog_context;
- последующие вопросы ("что это за продукт?", "расскажи про него", "дай комплект") продолжают работать без повторного выбора продукта.

Таким образом реализовано продолжение сценариев после поиска документов

## 3. Расширение `_product_dialog_context`
Контекст продукта теперь используется не только для карточек продукта.

Он хранит состояние после:

- списка продуктов;
- карточки продукта;
- комплекта документов;
- сравнения продуктов;
- списков значений атрибутов.

В контексте сохраняются:

- список найденных продуктов;
- выбранный продукт;
- последний режим работы (last_mode).

Это позволяет использовать предыдущие результаты без повторного SQL-запроса при очевидном follow-up.

## 4. Межсессионное сохранение контекста
Добавлен механизм `_CROSS_SESSION_CACHE`
Назначение:

при возникновении новых ADK Session (например, после 409 Conflict) сохраняется последний рабочий контекст пользователя.

Кэш содержит несколько последних состояний пользователя и используется для восстановления диалога между различными экземплярами сессии.

Таким образом уменьшается вероятность полной потери контекста при повторной инициализации Session.

## 5. Автоматическое сохранение состояния Dispatcher
После каждого ответа автоматически сохраняются:
- последний route;
- последний intent;
- последний search_query.

Dispatcher получает эту информацию при следующем запросе и использует её для определения follow-up интентов.

## 6. Расширение Dispatcher prompt 
В `dispatcher_agent_prompt.md` добавлен отдельный блок работы с предыдущим контекстом.

Dispatcher теперь использует:

- `last_user_query;`
- `last_route;`
- `last_intent;`
- `last_search_query`;
- `last_product`;
- `last_document_list`.

Добавлены правила обработки:

- местоимений ("его", "нее", "них");
- порядковых ссылок ("первый", "второй", "последний");
- коротких реплик ("что дальше", "расскажи о нем", "открой файл");
- вопросов после скачивания документа;
- повторных обращений к ранее найденному продукту.

Благодаря этому большинство follow-up сообщений теперь маршрутизируются без потери контекста.

## 7. Улучшено определение продукта после скачивания документов

Если пользователь сначала скачивает документ, а затем задаёт вопрос:

```
   Что это за продукт?
```
или
```
   Расскажи про него
```
Dispatcher использует сохранённый `last_product` и автоматически строит запрос на карточку соответствующего продукта.

## 8. Follow-up doc_search в RootAgent

Ранее короткие команды по списку документов обрабатывались вне единого контекстного слоя на уроыне бота.

Это приводило к ложным срабатываниям: сообщение `3` могло уйти в скачивание даже без предыдущего doc_search.

### Новая схема (ветка `doc_follow_up_in_root`)

Follow-up списка документов перенесён в `RootAgent` по паттерну product follow-up.

**Порядок short-circuit после OWASP:**

1. `_get_explicit_intent_dispatch` — комплект, архивные, подтверждение после карточки;
2. `_product_followup_dispatch` — продуктовый контекст;
3. `_doc_list_followup_dispatch` — doc-list контекст;
4. `dispatcher_agent` LLM — только если предыдущие шаги не сработали.

**Gate doc-list контекста** (`_has_doc_list_followup_context`):

- `last_route == "doc_search"`;
- `last_document_list` непустой (фрагмент текста последнего ответа doc_search, до 1500 символов).

Без этого gate короткие команды не перехватываются и идут в обычную маршрутизацию.

**Что распознаёт `_doc_list_followup_dispatch`:**

| Сообщение | Intent | Reason |
|-----------|--------|--------|
| `ещё`, `еще`, `дальше`, `more`, `next` | `show_more` | `doc_list_followup_show_more` |
| `все`, `покажи все`, `all`, `полностью` | `show_all` | `doc_list_followup_show_all` |
| `3`, `1,3`, `первый`, `второй` | `file_download` | `doc_list_followup_download_by_rank` |

**Что не перехватывается:**

- «скачай его», «открой файл» без номера — не doc-list follow-up;
- любые команды без активного doc-list контекста.

**Сохранение контекста списка:**

- после успешного `doc_search` с новым списком в `last_document_list` пишется текст ответа;
- при follow-up intent'ах (`file_download`, `show_more`, `show_all`) `last_document_list` не затирается;
- при маршрутах `kb_answer`, `product_selection` и др. — `last_document_list` очищается;
- параллельно из doc_search-ответа извлекается `last_product` и обновляется `_product_dialog_context` для последующих продуктовых реплик.

**Изменения в боте:**

- убран early-exit `parse_download_ranks` до `adk.run()`;
- убран early-exit `SHOW_MORE_RE` / `SHOW_ALL_RE` до ADK;
- добавлена обработка `_bot_action` типов `download_by_ranks`, `show_doc_list_more`, `show_doc_list_all` после ADK.

## 9. Сохранена совместимость существующей логики
Все изменения реализованы без изменения существующей архитектуры RootAgent.

Не были изменены:

- продуктовый SQL;
- логика `product_selection_agent`;
- ядро `doc_search_orchestrator` (поиск и валидация списка);
- существующая маршрутизация для новых поисковых запросов.


Контекст используется как дополнительный источник информации для разрешения коротких follow-up запросов.

## 10. Свободные follow-up команды после карточки продукта
Поддерживать естсетсвенные короткие ответы пользователя без обязательного указания продукта.

```
Покажи продукты Fort Knox
↓
8914
↓
давай
```
после выбора продукта, агент сохраняет его и после короткого ответа, так как в диалоге агент написал что может выдать комплект документов, должен среагировать на простую команду "давай" а не только на "комплект" 

В рамках данного сценария использует информацию из диалога `last_product` и после карточки, считывая сигнал к активному действию переходит к выдаче комплекта документов.

# Что ещё необходимо реализовать
## 1. Resolver деиктических ссылок

Необходимо реализовать полноценный resolver коротких ссылок пользователя:

- первый;
- второй;
- последний;
- этот;
- тот;
- его;
- её;
- по нему;
- там.

Resolver должен использовать:

- `last_search_results`;
- `last_document_list`;
- `selected_product`;
- историю предыдущих результатов.
  
### дореализация поддержки словесных числительных
Необходимо расширить обработку порядковых номеров.

Например:

- первый;
- второй;
- третий;
- последний.

Они должны преобразовываться в соответствующие индексы элементов списка.

Для doc_search частично закрыто в `_extract_ranks_with_words` (ветка `doc_follow_up_in_root`): «первый», «второй» и т.п. работают в `_doc_list_followup_dispatch`. Для product follow-up и деиктических ссылок («его», «этот») resolver всё ещё нужен.

## 2. Small Talk на основе предыдущего продуктового ответа, Исправление повторного переспрашивания, чтобы сразу выдавал **Ответственный Игорь К.**
Если пользователь после получения списка продуктов задает вопрос без повторного указания продукта, агент должен использовать информацию из предыдущего ответа.

Сценарий
```
Пользователь:
Покажи активные детские продукты

Ответ:
Альфа Kids 5 лет
Альфа Kids+ 5 лет

↓

Пользователь:
Чем они отличаются?
```
Ожидаемое поведение

Ответ должен строиться на основании списка продуктов, сохраненного в предыдущем сообщении.

Не требуется повторная идентификация продуктов.

Не требуется новый поиск по всему каталогу.

Для формирования ответа должны использоваться:

- `last_search_results`
- `_product_dialog_context`
- `products`

После формирования ответа список продуктов должен остаться в контексте для последующих follow-up запросов. 

## 3. Выбор продукта внутри сравнения
Во время сравнения нескольких продуктов агент должен понимать, какой продукт пользователь выбрал далее.

Сценарий
```
Сравни UL Ежемесячный доход и UL Стратегия роста
↓
Где меньше рисков?
↓
Дай комплект
```
Ожидаемое поведение

После ответа

   Где меньше рисков?

агент определяет продукт по контексту прошлого своего ответа и выбирает наилучший выдает его пользователю 
Условно:
```
UL Ежемесячный доход
```
После этого необходимо чтобы автоматически обновились:

- `last_product`
- `selected_product`
- `_product_dialog_context`

Последующий запрос
```
Дай комплект
```
должен использовать уже сохраненный выбранный продукт без дополнительных уточнений.

Таким образом формируется естественная цепочка:
```
сравнение
↓
выбор продукта
↓
карточка
↓
комплект документов
```
