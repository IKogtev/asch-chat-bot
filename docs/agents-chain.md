# Описание реализации цепочки агентов

## 1. Назначение

Документ фиксирует архитектурные правила для реализации цепочки агентов в Google ADK.

Цель:
- разделить ответственность между агентами;
- убрать неоднозначность в маршрутизации;
- зафиксировать контракты между этапами;
- дать code assistant точную основу для генерации кода без догадок.

---

## 2. Состав агентов

### `owasp_agent`
Назначение:
- только проверка безопасности пользовательского запроса.

Не делает:
- поиск по базе знаний;
- поиск документов;
- маршрутизацию;
- формирование содержательного ответа пользователю.

---

### `dispatcher_agent`
Назначение:
- только классификация запроса;
- только выбор целевой ветки обработки.

Не делает:
- вызовы MCP;
- поиск документов;
- поиск ответа в KB;
- финальный ответ пользователю по существу вопроса.

---

### `doc_search_agent`
Назначение:
- только поиск документов;
- только выдача списка найденных документов в структурированном виде.

Не делает:
- проверку безопасности;
- маршрутизацию;
- длинные содержательные ответы по знаниям;
- скачивание файлов.

---

### `kb_answer_agent`
Назначение:
- только поиск ответа в базе знаний;
- только формирование текстового ответа по знаниям.

Не делает:
- проверку безопасности;
- маршрутизацию;
- выдачу списка документов как основной режим ответа;
- скачивание файлов.

---

## 3. Общие правила архитектуры

1. Существует одна внешняя точка входа в ADK-приложение.
2. Внешний Telegram-бот работает только с одним `root_agent`.
3. Оркестрация цепочки выполняется кодом, а не промптом.
4. Каждый агент имеет узкую специализацию.
5. Каждый этап возвращает строго определённый JSON-контракт.
6. Если этап вернул невалидный контракт, это считается ошибкой этапа.
7. Внутренние контракты агентов не должны смешиваться с финальным контрактом для бота.
8. Имена route, mode, intent и agent name используются только в `snake_case`.

---

## 4. Порядок выполнения цепочки

Порядок выполнения фиксированный:

1. `owasp_agent`
2. `dispatcher_agent`
3. один из:
   - `doc_search_agent`
   - `kb_answer_agent`

### Правила выполнения

- если `owasp_agent` вернул `status=blocked`, цепочка останавливается;
- если `owasp_agent` вернул `status=ok`, управление передаётся в `dispatcher_agent`;
- `dispatcher_agent` обязан выбрать ровно один route;
- одновременно запускать `doc_search_agent` и `kb_answer_agent` нельзя;
- финальный ответ наружу формируется только после завершения выбранной ветки.

---

## 5. Промпты

Промпты храним в папке:

```text
kb_storage/prompts
```

Формат именования:

```text
<agent_name>-prompt.md
```

Примеры:

```text
owasp_agent-prompt.md
dispatcher_agent-prompt.md
doc_search_agent-prompt.md
kb_answer_agent-prompt.md
```

Архивные копии:

```text
<agent_name>-prompt-old<YYMMDD>.md
```

Пример:

```text
dispatcher_agent-prompt-old260331.md
```

### Требования к промптам

Каждый промпт обязан:
- описывать только роль своего агента;
- не дублировать orchestration logic;
- не описывать поведение других агентов;
- требовать возврат строго заданного JSON;
- запрещать свободный текст, если ожидается JSON-контракт.

---

## 6. Модель

Все агенты используют общую модель через фабрику:

```python
build_common_model()
```

Требование:
- модель создаётся централизованно;
- параметры модели не дублируются внутри конкретных агентов без необходимости.

---

## 7. Инструменты

## 7.1. Общий принцип

Набор tools определяется отдельно для каждого агента.

Агенту разрешены только те инструменты, которые нужны для его роли.

---

## 7.2. Доступность инструментов

### `owasp_agent`
Доступные инструменты:
- нет MCP tools.

---

### `dispatcher_agent`
Доступные инструменты:
- нет MCP tools.

---

### `doc_search_agent`
Доступные инструменты:
- `kb_search`

Коллекция по умолчанию:
- `"documents"`

Назначение:
- поиск документов в базе документов.

---

### `kb_answer_agent`
Доступные инструменты:
- `kb_search`

Коллекция по умолчанию:
- `"knowledge_base"`

Назначение:
- поиск ответа в базе знаний.

---

## 7.3. Правила вызова `kb_search`

Нужно задокументировать в коде/рядом с кодом:
- точное имя tool;
- обязательные параметры;
- параметры по умолчанию;
- `top_k` по умолчанию;
- формат ожидаемого результата;
- допустимо ли переопределять collection.

Минимальное ожидаемое поведение:
- `doc_search_agent` вызывает `kb_search` только по коллекции документов;
- `kb_answer_agent` вызывает `kb_search` только по коллекции базы знаний;
- `dispatcher_agent` и `owasp_agent` не вызывают `kb_search`.

---

## 8. Route и intent

Чтобы не смешивать уровни логики, фиксируются две сущности:

### `route`
Технический маршрут выполнения следующего этапа.

Допустимые значения:
- `doc_search`
- `kb_answer`
- `reject`

---

### `intent`
Смысловой тип пользовательского запроса.

Допустимые значения:
- `doc_search`
- `kb_answer`
- `smalltalk`
- `blocked`

---

### Правило использования

- `dispatcher_agent` обязан возвращать `route`;
- `dispatcher_agent` может дополнительно возвращать `intent`;
- `smalltalk` не является отдельной веткой исполнения;
- `smalltalk` маршрутизируется в `kb_answer`.

---

## 9. Контракты агентов

## 9.1. Контракт `owasp_agent`

### Успешная проверка

```json
{
  "status": "ok",
  "route": "continue",
  "reason": "safe"
}
```

### Блокировка

```json
{
  "status": "blocked",
  "route": "reject",
  "reason": "prompt_injection",
  "user_message": "Запрос отклонён по соображениям безопасности."
}
```

### Правила
- `status` обязателен;
- `route` обязателен;
- `reason` обязателен;
- `user_message` обязателен только при блокировке.

---

## 9.2. Контракт `dispatcher_agent`

### Для поиска документов

```json
{
  "status": "ok",
  "route": "doc_search",
  "intent": "doc_search",
  "reason": "user asks to find or download documents",
  "search_query": "продукт Fort Knox"
}
```

### Для ответа по базе знаний

```json
{
  "status": "ok",
  "route": "kb_answer",
  "intent": "kb_answer",
  "reason": "user asks an informational question",
  "search_query": "что такое накопительное страхование жизни"
}
```

### Для smalltalk

```json
{
  "status": "ok",
  "route": "kb_answer",
  "intent": "smalltalk",
  "reason": "user greeting or general small talk",
  "search_query": "приветствие пользователя"
}
```

### Правила
- `status` обязателен;
- `route` обязателен;
- `intent` обязателен;
- `reason` обязателен;
- `search_query` обязателен для downstream-агента;
- `route` может быть только `doc_search` или `kb_answer`;
- `reject` возвращает только `owasp_agent`.

---

## 9.3. Контракт `doc_search_agent`

`doc_search_agent` возвращает не свободный текст, а структурированный результат поиска документов.

```json
{
  "status": "ok",
  "mode": "search_results",
  "message": "Вот найденные документы:",
  "results": [
    {
      "document_id": "doc_123",
      "source_name": "Памятка по продукту.pdf",
      "source_path": "products/fort-knox/Памятка.pdf",
      "snippet": "Краткий фрагмент текста документа",
      "rank": 1
    }
  ]
}
```

### Правила
- `status` обязателен;
- `mode` всегда равен `search_results`;
- `message` обязателен;
- `results` обязателен, даже если список пустой;
- `rank` должен быть целым числом, начиная с 1;
- `document_id` обязателен;
- `source_name` обязателен.

### Если ничего не найдено

```json
{
  "status": "ok",
  "mode": "search_results",
  "message": "Релевантные документы не найдены.",
  "results": []
}
```

---

## 9.4. Контракт `kb_answer_agent`

`kb_answer_agent` возвращает текстовый ответ в структурированном виде.

```json
{
  "status": "ok",
  "mode": "text_answer",
  "message": "Накопительное страхование жизни — это страховой продукт, который сочетает защиту и накопление средств."
}
```

### Правила
- `status` обязателен;
- `mode` всегда равен `text_answer`;
- `message` обязателен;
- `results` не используется.

### Если ответ не найден

```json
{
  "status": "ok",
  "mode": "text_answer",
  "message": "Не удалось найти точный ответ в базе знаний."
}
```

---

## 10. Финальный контракт для бота

Наружу из `root_agent` должен выходить единый финальный контракт.

```json
{
  "mode": "reject|text_answer|search_results",
  "message": "string",
  "results": []
}
```

### Режимы

#### `reject`

```json
{
  "mode": "reject",
  "message": "Запрос отклонён по соображениям безопасности.",
  "results": []
}
```

#### `text_answer`

```json
{
  "mode": "text_answer",
  "message": "Накопительное страхование жизни — это ...",
  "results": []
}
```

#### `search_results`

```json
{
  "mode": "search_results",
  "message": "Вот найденные документы:",
  "results": [
    {
      "document_id": "doc_123",
      "source_name": "Памятка.pdf",
      "source_path": "products/fort-knox/Памятка.pdf",
      "snippet": "Краткий фрагмент",
      "rank": 1
    }
  ]
}
```

### Правила
- бот должен ориентироваться только на этот финальный контракт;
- бот не должен пытаться угадывать тип ответа по свободному тексту;
- бот не должен зависеть от внутренних контрактов промежуточных агентов.

---

## 11. Обработка ошибок

Нужно явно зафиксировать fallback-правила.

### Ошибки контракта
Если агент вернул:
- невалидный JSON;
- JSON без обязательных полей;
- недопустимое значение `route`, `mode`, `status` или `intent`;

то это считается ошибкой этапа.

---

### Ошибки tool-вызова
Если `kb_search` завершился с ошибкой:
- ошибка логируется;
- пользователю возвращается безопасное сообщение без технических деталей;
- формат ответа всё равно должен соответствовать финальному контракту.

Пример:

```json
{
  "mode": "text_answer",
  "message": "Произошла ошибка при обращении к базе знаний. Попробуйте позже.",
  "results": []
}
```

---

### Ошибки маршрутизации
Если `dispatcher_agent` не смог выбрать корректный route:
- по умолчанию использовать безопасный fallback в `kb_answer`;
- ошибка должна быть залогирована.

---

## 12. Что ещё нужно задокументировать рядом с кодом

Нужно отдельно описать:

1. фабрики:
   - `build_common_model()`
   - `build_tools_for_agent(agent_name)`

2. функции валидации контрактов:
   - `validate_owasp_result(...)`
   - `validate_dispatcher_result(...)`
   - `validate_doc_search_result(...)`
   - `validate_kb_answer_result(...)`
   - `validate_final_bot_contract(...)`

3. orchestrator:
   - порядок вызова агентов;
   - преобразование внутренних контрактов в финальный контракт бота;
   - поведение на ошибках.

4. формат логирования:
   - какой агент вызван;
   - какой route выбран;
   - какой tool вызван;
   - сколько результатов найдено;
   - на каком этапе произошла ошибка.
