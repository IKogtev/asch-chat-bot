# WebUI «Настя» — анализ и план Релиза 2

Документ фиксирует разрыв между ТЗ и текущей реализацией, рекомендуемую архитектуру и объём работ. Цель: третий канал (Web) рядом с Telegram и MAX **без новой бизнес-логики агентов** и с минимальными правками существующих сервисов.

Источники:

- ТЗ «Техническое задание на разработку WebUI сервиса «Настя»» (revision 6, формулировки от 2026-08-20; вход по телефону назван «планируемой авторизацией», критерии приёмки те же)
- текущий `asch-chat-bot` (бот, ADK, kb-manager, БД)
- ветка `ag_ui/first_look`
- `platform-2/robot-v7-docs-handover` и `robot-v7-client-app` — только как справочник, не как шаблон для копирования

---

## 1. Короткий вывод

**Рекомендация:**

1. **WebUI — отдельный репозиторий** (Next.js / React). Экран диалога, формы входа, рендер `blocks`.
2. **`web-bff` — новый FastAPI-сервис в `asch-chat-bot`**. Это channel adapter для Web, как бот для Telegram/MAX, а не второй агент.
3. **Не ходить из BFF в Postgres «новым SQL»**. Переиспользовать Python-слой (`AdkApiClient`, сторы, `UserResolver`, документы) и вынести из `handlers.py` тонкий `run_turn()` / `apply_bot_action()`.
4. **`adk-agent` в Релизе 2 не менять**, кроме отдельного решения об изоляции контекста каналов (см. §5.4).
5. **AG-UI и CopilotKit в критический путь Релиза 2 не включать.** Они совместимы с Google ADK (официальный адаптер, middleware «существующий API → AG-UI events»). Для текущего ТЗ выгода меньше стоимости слоя. Второй процесс `root_agent` как в `first_look` не нужен ни сейчас, ни потом.

ТЗ описывает API авторизации, истории, сообщений и документов. Таких HTTP API нет: это логика внутри бота. BFF и становится этим API для браузера. Это не дублирование backend в смысле ТЗ.

```text
                   ┌─────────────────────┐
                   │   nastya-web-ui     │
                   │ React / Next.js     │
                   │ отдельный репозиторий │
                   └──────────┬──────────┘
                              │ HTTPS / cookie
                   ┌──────────▼──────────┐
                   │    web-bff          │
                   │    FastAPI          │
                   │ auth, DTO, files    │
                   └──────────┬──────────┘
                              │
                   ┌──────────▼──────────┐
                   │ shared python       │
                   │ run_turn / stores   │
                   └──────────┬──────────┘
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
     adk-agent            kb-manager          existing DB
      /run                documents           users / history
      later /run_sse
```

Браузер не должен знать: URL ADK, `app_name`, ADK `session_id`, токен KB, внутренние id Telegram/MAX, структуру `_bot_action`.

В Релиз 2 **не входят:** CopilotKit, AG-UI, Redis, Temporal, WebSocket, новый agent runtime, Keycloak. 

Точка расширения на будущее: `AdkTransport` сейчас, `AgUiTransport` позже по надобности, без смены DTO фронта.

## 2. Что есть сейчас

### 2.1. Каналы и идентичность

- Каналы: Telegram (`bot/bot_v6.py`) и MAX (`bot/max_bot.py`).
- Пользователь унифицируется по телефону (`UserResolver` → `users` + `user_accounts`).
- Телефон **не подтверждается кодом**. Пользователь жмёт «Поделиться контактом».
- Доступ: запись есть, `users.is_blocked = false`. Отдельного whitelist-HTTP API нет.
- Админка kb-manager (`ui_users` + JWT) — **другой контур**, к WebUI Релиза 2 не относится.

### 2.2. Как бот вызывает агента

`AdkApiClient`:

- `POST /apps/{app}/users/{user_id}/sessions/{session_id}`
- `POST /run` с `user_id`, `session_id`, текстом; история в ADK **не передаётся**
- профиль уходит через отложенный `stateDelta`

На каждый ход бот делает **новую** ADK-сессию: `{global_user_id}_{turn_id}`. Контекст диалога держится не ADK-сессией, а:

- `chat_history` в Postgres (лента канала и `/reset`);
- in-memory `_CROSS_SESSION_CACHE` в `RootAgent` по `clean_id = session_id.split("_")[0]` (сейчас это `global_user_id`);
- таблицами `search_meta` / `search_results` для списков документов.

Общего service layer почти нет: клиенты и сторы уже вынесены, оркестрация хода смешана с Telegram/MAX в `bot/services/handlers.py`.

### 2.3. Что бот делает после `/run` (этого нет в агенте)

Из `stateDelta._bot_action` бот:

| `type` | Действие |
|---|---|
| `send_product_kit` | файлы комплекта с диска / kb |
| `download_by_ranks` | скачивание через `DocumentHandler` → kb-manager |
| `show_doc_list_more` / `show_all` | пагинация сохранённого поиска |

Карточки, сравнения, таблицы — **markdown-текст** ответа `root_agent`, не отдельный JSON API.

### 2.4. Стриминг сейчас

Бот ждёт полный ответ `/run`. ТЗ требует индикатор «идёт обработка», не token-stream. Именованные стадии («ищем документы», «сравниваем» и т.п.) и стриминг токенов в Релиз 2 не входят.

## 3. Разрыв ТЗ ↔ реализация

| ТЗ | Факт | Что делать |
|---|---|---|
| OTP в ТГ/MAX через «существующий backend авторизации» | OTP нет | Новая логика в `web-bff` + отправка через Bot API |
| API текущего пользователя / истории / сообщения | Только внутренние вызовы бота | HTTP в `web-bff` над shared python |
| Карточки и сравнения как API | Markdown от агента | Рендер markdown в UI; BFF только нормализует в `blocks` |
| Поиск и скачивание документов | `_bot_action` + kb-manager | Shared `apply_bot_action()`, не расчёт на клиенте |
| Один пользователь — один диалог | В мессенджере лента канала своя | Web-лента **своя**; идентичность общая по телефону |
| Оценка ответа | Нет | Таблица + событие в `events` |
| Корп. почта `@alfastrah.ru` | Вне Релиза 2 | Не делать |
| Админка, новая БЗ, расчёт продуктов | Запрещены ТЗ | Не делать |

**Ограничение OTP:** код можно отправить, только если телефон уже привязан к Telegram и/или MAX. Саморегистрации с веба нет. Нет аккаунта — вход невозможен («проверка наличия доступа»).

## 4. Что дают прошлые наработки

### 4.1. `ag_ui/first_look`

Полезное:

- идея отдельного web-контура, не встроенного в kb-manager;
- паттерн карточек doc_search (`DocSearchCards` + `search_results`);
- черновик Next.js + Tailwind.

Не брать в Релиз 2 как основу:

- второй контейнер агента (`adk-ag-ui`) с тем же `root_agent`;
- CopilotKit как продуктный шелл (он владеет чатом; ТЗ просит шапку, один диалог, копирование, оценку, документы, быстрые действия).

### 4.2. robot-v7 (подсмотреть, не копировать)

Перенять принципы: UI в отдельном репо, браузер не ходит в агента, BFF держит секреты.

Не копировать: Temporal, Redis SSE, Runtime API, tenants, Keycloak, CopilotKit как обязательный транспорт.

### 4.3. AG-UI / CopilotKit — совместимость vs окупаемость

На 2026 AG-UI официально поддерживает Google ADK. Протокол рассчитан на адаптацию существующих agent backends, в том числе middleware: существующий API → AG-UI events. Второй экземпляр `root_agent` для этого не требуется.

CopilotKit frontend/runtime построен вокруг AG-UI. Будущая схема:

```text
сейчас:  React WebUI → web-bff → AdkTransport → ADK /run
потом:   React / CopilotKit → Copilot Runtime → AG-UI adapter → тот же ADK
```

Агента ради CopilotKit переписывать не нужно. OTP, пользователь, история канала, права на файлы, `_bot_action` всё равно останутся в BFF.

**Вывод:** не подключать в Релизе 2 не из-за технической несовместимости, а потому что ТЗ этого не оправдывает.

## 5. Рекомендуемая архитектура

### 5.1. Почему прокладка, а не правки `adk-agent`

`adk-agent` — оркестратор LLM. Канальный слой (кто пользователь, OTP, файлы, пагинация, лента UI) уже живёт в боте. Если встроить это в агент, смешаются оркестрация и доставка.

### 5.2. Shared python, не прямой SQL из BFF

Сейчас можно переиспользовать как есть:

| Модуль | Роль |
|---|---|
| `bot.services.database.AdkApiClient` | `/run`, сессии, `stateDelta` |
| `bot.services.database.PostgresChatStore` | `chat_history`, search_* |
| `bot.services.user_resolver.UserResolver` | склейка по телефону |
| `bot.services.adk_events.extract_bot_action` | разбор `_bot_action` |
| `utils.document_handler.DocumentHandler` | скачивание через kb-manager |
| `bot.services.product_kits.get_product_kit` | комплект файлов |
| `bot.services.utils.normalize_phone` | нормализация номера |
| `handle_download_by_ranks` / `handle_show_more` / `handle_show_all` | follow-up документов (отрезать `bot_res.send`) |

Вынести из `handlers.py` без большого рефакторинга бота:

```text
channel/                 или bot/services/dialog.py
  run_turn()             profile → /run → action → history
  apply_bot_action()     kit / download / show_more
```

Telegram и MAX могут перейти на `run_turn()` позже. В Релизе 2 достаточно, чтобы BFF импортировал этот слой, а текущие боты не ломались.

**web-bff остаётся в `asch-chat-bot`**, потому что это Python и импорт shared-слоя. Второй репозиторий для BFF имеет смысл, только если его перепишут на Node. UI — отдельный репо.

### 5.3. Почему UI в отдельном репо

Другой стек и ритм релизов; монолит уже тяжёлый (kb/prompts/mcp); фронт не тянет секреты ADK/KB. В `asch-chat-bot` остаются BFF, миграции, compose/k8s.

Компромисс на 1–2 спринта: заготовка UI в `web/`, затем вынос. Для Релиза 2 лучше сразу отдельный репо, чтобы не повторить `web/copilot-web`.

### 5.4. Где живёт BFF: отдельный процесс, не порт бота

У Telegram-бота HTTP `:8001` — рассылка. Auth/chat туда нельзя: рестарт поллинга роняет WebUI.

`web-bff` — отдельный FastAPI. Токены Telegram/MAX только для `sendMessage` (OTP). Это не второй long-poll.

### 5.5. Идентичность, лента, контекст агента

Это **три разные вещи**.

| Что | Между каналами |
|---|---|
| Пользователь (`users.id`, телефон, `is_blocked`) | общий |
| Видимая лента | **своя на канал** (как ТГ vs MAX) |
| Контекст агента (`last_product`, `_product_dialog_context`, список документов) | сейчас общий из-за `clean_id = split("_")[0]`; **для Web лучше изолировать** |

Общий контекст без общей ленты выглядит как баг: на вебе «скачай» / «карточку» внезапно про продукт из Telegram. Особенно опасны ranks документов — номера относятся к списку, который показали в другом чате.

Надёжная изоляция — маленькая правка `rootagent` (ключ кэша = пользователь + канал) и тот же канал в выборке `search_meta`. Без этого изоляция дырявая. Это **не блокер каркаса BFF**, но решение нужно до продуктового follow-up на вебе.

Пока правка агента не сделана, не копировать слепо `session_id = {global_user_id}_{turn_id}` для Web — иначе контекст с мессенджерами общий.

`/reset` в боте чистит общую `chat_history` и RAM-кэш. При раздельных лентах reset канала не должен молча стирать другой.

## 6. Target design: контракт BFF

Браузер видит только этот API. Cookie `HttpOnly` + `Secure` + `SameSite=Lax`.

BFF — **normalizer**, не выполняет никакой бизнем логики. Только: OTP (одноразовый пароль), сессия веба, вызов shared `run_turn()`, сборка DTO, выдача файлов.

### 6.1. Endpoints

| Метод | Назначение |
|---|---|
| `POST /auth/otp/request` | телефон → нормализация → не blocked → OTP в ТГ и/или MAX |
| `POST /auth/otp/verify` | код → cookie |
| `POST /auth/logout` | выход |
| `GET /me` | id, имя, маска телефона |
| `GET /dialog` | лента **web-канала** + пагинация вверх |
| `POST /dialog/messages` | ход; сейчас request → waiting → complete |
| `GET /files/{token}` | download после проверки cookie |
| `POST /dialog/messages/{id}/feedback` | оценка ответа |

Правила OTP: 4–6 цифр, TTL 5–10 мин, лимит попыток, только хеш, анти-перебор, одинаковый ответ «нет доступа», нет ТГ/MAX — явная ошибка «сначала войдите в бота и поделитесь телефоном».

### 6.2. Channel-neutral DTO (`blocks`) (Data Transfer Object - контейнером для данных, которые нужно передать между разными частями приложения)

Не Telegram HTML и не типы CopilotKit.

```json
{
  "message_id": "...",
  "status": "complete",
  "blocks": [
    {"type": "text", "content": "..."},
    {"type": "product_card", "data": {}},
    {"type": "documents", "items": []},
    {"type": "suggestions", "items": []}
  ],
  "error": null
}
```

- `text` — markdown агента (заголовки, списки, таблицы, «карточки» сравнений).
- `documents` — из `_bot_action` + `search_*` после shared-слоя, с URL на `/files/...`.
- `product_card` — только если данные уже пришли от агента/action; не считать на BFF.
- `suggestions` — опционально. Статические чипы на клиенте; контекстные («Сравнить с Unit Linked») из `last_product` / `clarification_options` правилами BFF. Клик = обычный `POST /dialog/messages`. Не критерий приёмки Релиза 2.

Позже тот же ресурс может стримить статусы **той же предметной модели**, не ломая фронт:

`started` → `status` (стадия) → `text_delta` → `documents` → `complete`


### 6.3. Что менять в репозиториях

| Место | Релиз 2 |
|---|---|
| `adk-agent` / `root_agent` | По умолчанию не трогать. Изоляция канала — отдельный маленький патч + `search_meta`. |
| `handlers.py` | Вынести `run_turn` / `apply_bot_action`; боты пока могут звать старый путь |
| Telegram / MAX | Не трогать runtime; OTP шлёт BFF через Bot API |
| kb-manager / MCP | Не трогать |
| kb-file-ui / adk-web | Не трогать |
| Postgres | `web_sessions`, `otp_challenges`, `message_feedback`; при изоляции ленты — канал в истории (новая колонка или отдельная выборка web), **не** смешивать с ТГ в UI |
| новый пакет | `web_bff/` + тонкий `channel/` / `bot/services/dialog.py` |
| k8s / compose | сервис `web-bff`, ingress UI |

Черновик размещения в `asch-chat-bot`:

```text
bot/services/dialog.py   # run_turn, apply_bot_action
web_bff/
  app.py
  auth_otp.py
  dialog.py              # HTTP → dialog.py shared
  files.py
  dto.py                 # blocks
  messenger_otp.py
```

## 7. WebUI (отдельный репо)

Стек: Next.js App Router + TypeScript + Tailwind. Node только как proxy на BFF (cookie/CORS). Бизнес-логики на Node нет.

Экраны Релиза 2: телефон → OTP → один диалог (шапка, лента, ввод, индикатор, статические быстрые действия, копирование, скачивание, оценка, выход).

Вёрстка: не pixel-perfect. Рендер задаёт направление. Элементы макета вне ТЗ (новости, «новый диалог», колокольчик) **не входят** автоматически.

Desktop: header + чат + опциональный сайдбар. Сразу заложить responsive (планшето/мобильный стек: sticky input, карточки столбиком, таблицы с горизонтальным скроллом), без отдельного «мобильного продукта». Специализированное мобильное представление — более поздние релизы.
Плашки файлов и карточка в ленте — кастомные React-блоки из `blocks`, не CopilotKit.

## 9. Этапы

### Этап 0 — согласования

1. OTP только для уже известных телефонов с ТГ/MAX — **да**.
2. Лента Web своя, не общая `chat_history` с мессенджерами — **да**.
3. Контекст агента для Web изолировать (патч ключа кэша + search) — **да, до follow-up документов/карточек**.
4. Оценка ответа — простая, в объёме UI из §4 ТЗ.
5. UI — отдельный GitLab-репо; BFF — в `asch-chat-bot`.

### Этап 1 — shared слой + `web-bff` без UI

- `run_turn` / `apply_bot_action`.
- OTP + cookie (в dev допустим stub доставки).
- `GET /me`, `GET /dialog`, `POST /dialog/messages` → DTO `blocks`.
- Тесты: телефон, blocked, разбор action, нормализация DTO.

Критерий: curl «известный телефон → сообщение → ответ + file URL».

### Этап 2 — UI вход и один диалог

Формы, лента, индикатор, ошибки без стека, копирование, выход.

### Этап 3 — документы и богатый ответ

Markdown/таблицы, плашки файлов, статические чипы, оценка.

## 10. Риски

| Риск | Почему | Митигация |
|---|---|---|
| OTP некому отправить | Нет контакта в боте | Ясный текст; вход в бота — предусловие |
| Общий контекст без общей ленты | `clean_id` = UUID | Изоляция ключа кэша и `search_meta` по каналу |
| `{id}_{channel}_{turn}` «изолирует» | `split("_")[0]` отбрасывает канал | Не использовать этот трюк |
| Дубль SQL в BFF | Логика размазана по handlers | Shared `run_turn`, не новые запросы «с нуля» |
| Долгий `/run` | Как в боте | Индикатор, `ADK_TIMEOUT_SEC`, повтор |
| Второй процесс агента | Ошибка first_look | Один `adk-agent` |
| CopilotKit как шелл | Мало экономит на OTP/файлах | Свой чат, DTO из блоков |
| Утечка ADK/KB в браузер | Прямые вызовы | Только BFF |

## 11. Критерии приёмки (ТЗ §7) → где закрываются

| Критерий | Где |
|---|---|
| Вход по телефону + OTP | `web-bff` + UI |
| После входа один диалог | `GET /dialog` (лента web) |
| Вопрос → ответ | `POST /dialog/messages` → shared `run_turn` → ADK `/run` |
| Уточнения с контекстом | контекст **web-канала** |
| История после F5 и повторного входа | лента канала + cookie |
| Текст, списки, таблицы, карточки, сравнения | markdown / `blocks` в UI |
| Найти и скачать документ | `apply_bot_action` + `/files` |
| Копирование ответа | UI |
| Ноутбук, Chrome/Edge | UI |

Отсутствие динамических чипов не блокирует приёмку.
