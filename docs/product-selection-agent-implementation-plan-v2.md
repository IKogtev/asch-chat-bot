## 3. Целевые intents и режимы

В `dispatcher_agent` должны остаться только эти product intents:

- `product_card` - карточка или основные свойства конкретного продукта;
- `product_kit` - комплект материалов по конкретному продукту;
- `product_filter` - список продуктов по параметрам;
- `product_compare` - сравнение продуктов или групп продуктов.

Удалить из dispatcher, root state, промптов и тестов:

- `product_recommendation`;
- `product_explanation`;
- `product_alternatives`.

В `product_selection_agent` должны остаться только эти режимы:

- `product_card`;
- `product_kit`;
- `product_filter`;
- `product_compare`;
- `needs_clarification`;
- `no_data`.

`needs_clarification` - это не intent диспетчера, а режим ответа продуктового агента, когда найдено несколько подходящих продуктов и нужно уточнить срок или валюту.

## 4. Целевой контракт `product_selection_agent`

Поле `source` убрать. Агент всегда работает с одним источником продуктовых данных, поэтому источник не несет полезной информации и только усложняет валидацию.

Базовый JSON-контракт:

```json
{
  "status": "ok",
  "mode": "product_card",
  "message": "Короткий ответ пользователю",
  "used_tables": ["products"],
  "resolved_product": {
    "id": "2832",
    "name": "Fort Knox 6 месяцев"
  },
  "clarification_options": []
}
```

Правила:

- `status` всегда `"ok"`;
- `mode` только из списка выше;
- `message` обязателен и не пустой;
- `used_tables` нормализуется в массив строк;
- для `product_card` и `product_kit` при однозначно найденном продукте нужен `resolved_product`;
- для `product_kit` нужен `resolved_product.id`, потому что папка комплекта называется по ID продукта;
- для `needs_clarification` нужен непустой `clarification_options`;
- для `no_data` `used_tables` может быть пустым, `resolved_product` не нужен;
- `source` запрещен как лишнее поле.

`clarification_options` должен содержать только данные, найденные в классификаторе:

```json
[
  {
    "id": "2832",
    "name": "Защищенный капитал 5 лет",
    "term": "5 лет",
    "currency": "рубли"
  }
]
```

## 5. Комплекты материалов

Переменную каталога комплектов нужно инициализировать так:

```text
PRODUCT_KITS_ROOT=kb_storage\kb\Комплекты документов по продуктам
```

Русские буквы и пробелы в пути не проблема, если соблюдать несколько условий:

- все редактируемые файлы с этим значением сохраняются в UTF-8;
- в Python используется `pathlib.Path`, а не ручная склейка строк;
- в Docker/Kubernetes путь передается как обычная строка env и не режется shell-скриптами без кавычек;
- при сравнении путей используется `resolve()` и проверка, что итоговый путь остается внутри `PRODUCT_KITS_ROOT`;
- тесты создают временные папки с кириллицей и пробелами, чтобы защитить этот сценарий.

Сервис комплекта должен быть детерминированным, без LLM:

1. На вход получает `id` из `resolved_product`.
2. Строит путь `PRODUCT_KITS_ROOT / product_id`.
3. Проверяет, что путь не выходит за пределы `PRODUCT_KITS_ROOT`.
4. Проверяет наличие папки.
5. Собирает файлы комплекта.
6. Отбрасывает скрытые и служебные файлы.
7. Ограничивает количество и размер файлов.
8. Возвращает структурированный результат: найдено, нет папки, папка пустая, есть файлы, часть файлов невалидна.

Первый уровень вложенности предпочтителен. Рекурсивный обход стоит включать только если структура комплектов реально хранит файлы во вложенных папках.

## 6. Форматирование ответов

К форматированию нужно подойти системно, а не решать его только в промпте `product_selection_agent`.

### 6.1. Проблема

Сейчас разные агенты могут возвращать Markdown, HTML-подобный текст или обычный текст. Бот затем применяет `markdown_to_safe_html`, но Markdown-таблицы и длинные строки плохо контролируются в Telegram/Max.

Для продуктовых сценариев v2 это особенно важно, потому что постановка требует карточки и таблицы сравнения/фильтрации.

### 6.2. Варианты

Вариант 1: только промпты.

- В промптах всех leaf-агентов описать единый формат: короткий Markdown без таблиц, `**bold**`, `*italic*`, списки, без HTML.
- Плюсы: быстро.
- Минусы: формат остается вероятностным, сложнее тестировать.

Вариант 2: централизованный форматтер.

- Агент возвращает структурированные данные или строго ограниченный текст.
- Root/bot вызывает общий форматтер, например `utils/bot_response_format.py`.
- Форматтер строит bot-safe HTML для Telegram/Max.
- Плюсы: тестируемо, единый формат, меньше зависимости от LLM.
- Минусы: нужно расширить контракт агента для структурированных данных или хотя бы ввести форматные helpers.

Вариант 3: гибрид.

- В промптах всех агентов закрепить единый допустимый формат.
- Для продуктового агента дополнительно сделать детерминированные render-функции для карточки, фильтра, сравнения и уточнения.
- Root форматирует продуктовые ответы через эти функции, а остальные агенты пока проходят через общий безопасный Markdown-to-HTML слой.

Рекомендуемый вариант: гибрид.

### 6.3. Что добавить

1. Создать общий модуль форматирования, например `utils/bot_response_format.py`.
2. Описать единый bot-safe subset:

   - `**bold**` только для заголовков и названий;
   - `*italic*` для источника/ограничений;
   - короткие списки вместо широких таблиц;
   - максимум 5-7 строк в одном блоке;
   - без внутренних технических полей.
3. Обновить промпты:

### Этап 6. Интеграция root, ADK-клиента и bot

Сценарий комплекта нельзя надежно реализовывать через парсинг служебных маркеров из текста. Интеграцию нужно делать по аналогии с `doc_search`: агент/root формирует структурное состояние, а bot после `adk.run()` читает это состояние из ADK events и выполняет отправку файлов сам.

Целевой поток:

1. Пользователь пишет: "Дай комплект для продукта 2832".
2. `dispatcher_agent` возвращает:

```json
{
  "status": "ok",
  "route": "product_selection",
  "intent": "product_kit",
  "reason": "...",
  "search_query": "продукт 2832"
}
```

3. `RootAgent` вызывает `product_selection_agent`.
4. `product_selection_agent` возвращает:

```json
{
  "status": "ok",
  "mode": "product_kit",
  "message": "Нашел продукт Fort Knox 6 месяцев. Отправляю комплект материалов.",
  "used_tables": ["products"],
  "resolved_product": {
    "id": "2832",
    "name": "Fort Knox 6 месяцев"
  },
  "clarification_options": []
}
```

5. `RootAgent` кладет пользовательский текст в `_root_final_text`.
6. `RootAgent` дополнительно кладет в session state служебное действие `_bot_action`:

```json
{
  "type": "send_product_kit",
  "product_id": "2832",
  "product_name": "Fort Knox 6 месяцев"
}
```

7. `AdkApiClient.run()` оставляет совместимый возврат `(answer, events)`. Нужно добавить в `AdkApiClient` helper, который извлекает `_bot_action` из `events`, как bot сейчас извлекает факт нового `doc_search` через сохраненное состояние:
   - просмотреть `actions.stateDelta`;
   - просмотреть `actions.state_delta`;
   - при необходимости просмотреть другие поля события, если фактический ADK response хранит state delta иначе.
8. В `bot/services/handlers.py` после `adk.run()`:
   - если `bot_action.type == "send_product_kit"`, сначала отправить `answer`;
   - вызвать сервис комплекта с `product_id`;
   - отправить все найденные файлы;
   - если файлов нет, отправить сообщение сервиса;
   - залогировать результат;
   - не запускать обычный doc_search rendering.
9. Если `mode="needs_clarification"`, `_bot_action` не создается: бот отправляет только уточняющий `answer`.
10. Если `mode="no_data"`, `_bot_action` не создается: бот отправляет только сообщение об отсутствии данных.

Почему так:

- пользовательский текст остается чистым;
- bot не парсит JSON из сообщения;
- отправка файлов тестируется отдельно;
- root отвечает за решение "нужно действие", bot отвечает за выполнение действия;
- подход остается тем же, что у `doc_search`: структурное состояние отдельно от пользовательского текста.

Unit-тесты для этапа:

- `RootAgent` создает `_bot_action` для `product_kit`;
- `RootAgent` не создает `_bot_action` для `product_card`, `product_filter`, `product_compare`, `needs_clarification`, `no_data`;
- `AdkApiClient` извлекает `_bot_action` из событий ADK;
- handler при наличии `send_product_kit` вызывает сервис комплектов и отправляет файлы;
- handler при ошибке сервиса отправляет понятное сообщение и логирует сбой.

## 8. Риски

- Если в классификаторе нет стабильного ID продукта, UC-02 нельзя надежно реализовать без справочника соответствия продукт -> папка.
- Если папки комплектов называются не по ID продукта, нужен явный mapping в таблице или конфиге.
- Если ADK events не содержат state delta с `_bot_action`, придется расширять `AdkApiClient` другим способом: отдельным endpoint чтения state после run или явным структурным ответом ADK.
- Если Markdown-таблицы плохо отображаются в Telegram/Max, продуктовые таблицы нужно рендерить как списки/секции через форматтер.
- Если путь `kb_storage\kb\Комплекты документов по продуктам` не смонтирован в контейнер бота, сервис комплектов будет работать в unit-тестах, но не в runtime.
